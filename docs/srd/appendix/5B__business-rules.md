# BUSINESS RULES (from the 5B draft)

##### A. Normative rules for the Nexus implementation (consolidated from the screens and the reference backend)

Labels: **[O]** implemented in the Nexus LP UI mock; **[I]** implemented only in the reference backend or stated by the design documents; **[P]** proposed. Where the reference backend is known to be wrong or incomplete, the rule says so and states the Nexus behaviour to build.

**A1. Scope, entitlement and operating model**

- BR-137: Every LP request is resolved as user → active membership → organisation (client) → fund entitlement → resource. Client and fund identifiers sent by the browser are advisory; the server recomputes the allowed set and answers a generic 404 for anything outside it (403 `LP_FORBIDDEN` only for an explicit fund filter the user is not entitled to). **[I]** (reference: 403 for explicit `fundId`, silent filtering for lists, no check on ledger detail, vault list, request replies — Nexus must apply it uniformly)
- BR-138: A membership's `fundIds` is an explicit subset of the organisation's fund commitments; an empty or null list means no fund access in Nexus (the reference treats empty as all funds, which lets a scoped manager create an unscoped colleague). **[P]**
- BR-139: The funds in the session are the organisation's commitments in status ACTIVE or PENDING, filtered by the membership scope, one row per fund (the reference returns only the first commitment amount when a fund has several). **[I]**
- BR-140: Each fund carries an operating model, PRIVATE_CAPITAL or OPEN_ENDED. Private-capital funds show commitment, called, paid-in, unfunded, distributions, NAV, net IRR, TVPI, DPI and RVPI; open-ended funds show account value, units held, NAV per unit, YTD return and dealing, and their IRR, TVPI, DPI and RVPI are null (shown "—", never 0). **[I]** The Nexus UI shows the private-capital tiles for open-ended funds as well. DEFECT in 5.B.1.
- BR-141: A consolidated view ("All Funds") sums money across funds and recomputes TVPI, DPI and RVPI from the sums; net IRR is computed from the merged dated cash flows, not taken from one fund or averaged. **[P]** (reference: last fund's IRR)

**A2. As-of date and valuation status**

- BR-142: Every valuation figure is read from an approved, immutable snapshot (client, fund, as-of date, valuation status, calculation date, version, source module, approver). The requested as-of date selects the latest approved snapshot dated on or before it; a published snapshot is never recalculated, and a restatement is a new snapshot that supersedes the original while the original stays visible. **[I]** (reference: performance honours `asOfDate`; dashboard always takes the latest snapshot)
- BR-143: Valuation status vocabulary ESTIMATED, PROVISIONAL, FINAL, RESTATED; a figure is never shown without its status and as-of date; PROVISIONAL and ESTIMATED are visually distinct from FINAL. **[I]** (the reference only ever emits FINAL, plus UNAVAILABLE for benchmarks)
- BR-144: The default status of a mixed set of funds is the least certain status among them (ESTIMATED, then PROVISIONAL, then FINAL), not FINAL. **[P]** (reference: FINAL unless all funds agree)
- BR-145: The default as-of date is the latest approved as-of date among the in-scope funds; the user's `defaultAsOfPreference` (LATEST, LATEST_FINAL, a fixed month-end) is applied when the session is built. **[P]**

**A3. KPI and ledger formulas**

- BR-146: Unfunded commitment = total commitment − called capital (never − paid-in). Outstanding called = max(0, called − paid-in). Paid-in = Σ received payments on the investor's allocations. Called counts only calls visible to the investor. **[I]**
- BR-147: DPI = distributions ÷ paid-in; RVPI = NAV ÷ paid-in; TVPI = (distributions + NAV) ÷ paid-in; each is null when paid-in ≤ 0 or the fund is open-ended; ratios are decimal strings to 4 dp. **[I]**
- BR-148: Net IRR is computed from the investor's dated cash flows with the ending NAV as terminal value, stored as a decimal fraction (0.1840 = 18.4 %) to 4 dp; the UI multiplies by 100 only for display. The reference stores a percent number for computed values (16.7) and a fraction for seeded values; Nexus must use one convention. **[P]**
- BR-149: Open-ended account value = Σ over share classes of units × NAV per unit (never summed before pricing); YTD return = NAV per unit now ÷ NAV per unit at the prior 31 December − 1 (1M, 3M, 1Y and since-inception analogously); distributions use the fund-approved total-return method. **[I]** (reference: always 0)
- BR-150: Capital-call allocation is pro-rata by commitment: call amount = min(round2(commitment × call percent ÷ 100), commitment − Σ prior calls), rounded half-up to 2 dp, skipped when ≤ 0; the sum of allocations equals the call total or the remainder goes to the last investor. **[I]**
- BR-151: Distribution split: net to investors = gross − carry (carry = (gross − hurdle) × carry rate); each investor's share is pro-rata by paid-in (by commitment when no paid-in), rounded half-up, last investor takes the remainder. The investor sees gross (their share before adjustments), adjustments (withholding or fees, stored, not derived) and net paid. **[I]**/[P] (reference derives "adjustments" from unpaid remainder)
- BR-152: The investor ledger is read from posted records (calls, payments, distributions, payouts, subscriptions, redemptions, fees); amounts keep their original currency and amount, the historical conversion rate and its date, and the reporting amount; ledger rows are never restated by later FX. **[I]** (reference: no FX fields)

**A4. Capital calls and distributions (investor actions)**

- BR-153: A call or distribution is visible to investors only after staff approval and issue; drafts and cancelled records never appear in lists, summaries, notifications, activity or the ledger. **[I]** (reference applies this to calls only, and not to the ledger and activity feeds)
- BR-154: Acknowledging a call records who and when; it needs the SIGNATORY or MANAGER role and the call must be issued and not cancelled; it never changes `paid` or the status other than the acknowledged marker; a second acknowledgement returns 409 `LP_CALL_ALREADY_ACKNOWLEDGED` (per allocation, by anyone in the organisation). **[I]**
- BR-155: A payment confirmation is evidence only (file, claimed amount, notes, SHA-256, uploader, time). It does not change `paid`; staff matching does. Accepted file types and size are limited (default 25 MB; PDF, image, CSV, XLSX), the file is scanned before it is available, and a second confirmation for the same call is allowed. **[P]** (reference: no type check, no scan, no staff queue)
- BR-156: Derived call status order (target): CANCELLED, then PAID (paid ≥ amount > 0), then PARTIALLY_PAID (paid > 0), then OVERDUE (due date before today and unpaid), then ACKNOWLEDGED, then ISSUED. Acknowledgement must not hide an overdue call. **[P]** (reference puts ACKNOWLEDGED above OVERDUE)
- BR-157: "Due soon" is a configured window (default 7 days) used identically by the row highlight and by the summary (the UI uses 7, the reference summary 14). **[P]**
- BR-158: A call number is a sequential, per-fund number (CC-013). **[P]** (reference: derived from the date; no column)
- BR-159: Notice and statement downloads are real documents (PDF) generated or attached by staff; the reference returns text stubs. **[P]**

**A5. Dealing (subscriptions and redemptions)**

- BR-160: A request is created only from a valid estimate: estimate → snapshot (id, client, fund, type, canonical payload hash, result, expiry 15 minutes) → submit with `estimateSnapshotId`. The hash is computed over a fixed canonical field list that excludes `estimateSnapshotId`; a snapshot is single-use; the server repeats every check at submit time. **[I]**/[P] (reference: redemption hash can never match; snapshot reusable)
- BR-161: Estimates never allocate units, never change the ledger and always carry `isEstimate: true`; units and settlement become final only after funds are received and the dealing-date NAV is approved. **[I]**
- BR-162: Subscription estimate: management or subscription fee = amount × fee rate; other fees = flat fee; units = amount ÷ NAV per unit (fees are added on top, total investment = amount + fees); NAV per unit has 8 dp, units 6 dp, money 2 dp; NAV comes from the fund and share class dealing NAV, never a constant. **[I]** (the mock deducts fees from units; the reference uses NAV 1 when there is no holding) Q-NEW in 5.B.5.
- BR-163: Redemption estimate: mode AMOUNT (units = amount ÷ NAV), UNITS (value = units × NAV) or FULL (all units and the whole account value); fee = value × redemption fee rate; settlement amount = value − fee; settlement date = earliest dealing date + settlement lag business days (seed 2, design 3; the reference hard-codes 3 calendar days). **[I]**/[P]
- BR-164: Minimum balance: unless the redemption is FULL, the remaining account value must be at least the minimum balance amount and the remaining units at least the minimum balance units (defaults 1,000,000.00 and 100,000 units in the reference; both must hold). Breach returns 422 `LP_MIN_BALANCE_BREACH`. **[I]**
- BR-165: Available to redeem = max(0, account value − minimum balance amount), net of unsettled redemption requests, so that several pending requests cannot together exceed the position; available units = that value ÷ NAV. **[P]**
- BR-166: Notice period and dealing windows: the earliest dealing date must be on or after the first dealing date of the fund's frequency (default MONTHLY_LAST_BUSINESS_DAY) that falls on or after submission date + notice days (default 30 calendar days), evaluated on the fund calendar and cut-off time zone; otherwise 422 `LP_NOTICE_PERIOD`. **[P]** (reference: only today + notice days; frequency is informational; no cut-off time)
- BR-167: Compliance gate on estimate and submit: legal hold → 403 `LP_COMPLIANCE_HOLD`; dealing suspended → 403 `LP_DEALING_SUSPENDED`; inactive investor account → 409 `LP_ACCOUNT_INACTIVE`; not accredited, KYC not current and past-due unsettled capital calls are also enforced. **[P]** (reference: only the first three; KYC, accreditation and unsettled calls are display-only; unsettled calls always "true")
- BR-168: A submit for a source or destination bank account requires an ACTIVE account of the same client and fund scope. **[P]**
- BR-169: The dealing status workflow is staff-driven: SUBMITTED → COMPLIANCE_REVIEW → AWAITING_FUNDS → FUNDS_RECEIVED → AWAITING_NAV → ALLOCATED (subscription); SUBMITTED → COMPLIANCE_REVIEW → UNDER_REVIEW → AWAITING_NAV → ALLOCATED → SETTLED (redemption); REJECTED and CANCELLED terminal. **[I]**/[P] (reference: only SUBMITTED exists)

**A6. Currency**

- BR-170: Four currencies are kept apart: transaction currency, fund base currency, investor reporting currency and the temporary display currency (`presentationCurrency`). Display currency changes presentation only, never records. **[I]**
- BR-171: Conversion uses the FX rate of the snapshot or transaction date, stored with the record; a missing rate shows the original currency with a note, never a silent USD value. **[P]** (reference: ZIG falls back to USD with "FX rate unavailable")
- BR-172: Money formatting uses the row's currency symbol; the compact format must not hard-code "$". **[P]** DEFECT in the mock formatter.

**A7. Idempotency**

- BR-173: `Idempotency-Key` (8 to 200 printable ASCII characters) is required on: acknowledge call, upload payment confirmation, submit subscription, submit redemption, request performance report, acknowledge notice, create request, submit bank-instruction change, invite colleague. Scope = client + action + method + path + key; the same key and the same canonical payload (for multipart: fields plus file SHA-256) replays the first 2xx response with `Idempotent-Replay: true`; the same key with a different payload returns 409 `LP_IDEMPOTENCY_KEY_REUSED`; keys expire after a configured TTL (default 24 hours); the insert is atomic (unique scope + key) so two concurrent first requests execute once. **[I]**/[P] (reference: no TTL, fire-and-forget, multipart hashed before parsing)

**A8. Downloads, previews and integrity**

- BR-174: Every document view, preview and download is audited (user, action VIEW, PREVIEW or DOWNLOAD, time, IP, user agent) after the file has been served successfully; the detail shows the last 20 entries with user names, not ids. `secureDownloadsYtd` counts DOWNLOAD rows of the calendar year. **[I]**
- BR-175: Downloads are entitlement-checked at issue time and either streamed or served by a user-bound, short-lived (≤ 300 s) signed URL; file name and `Content-Type` come from the stored name and MIME type (the reference names every file `.bin` because MIME is never stored). Preview is limited to PDF and image types and returns 415 `LP_UNSUPPORTED_MEDIA` otherwise. **[P]**
- BR-176: Each document stores SHA-256, MIME type, size and page count at publication; the vault `verify` call recomputes the hash of the stored bytes and returns `verified`, `expectedSha256`, `actualSha256`. **[I]**
- BR-177: Uploads (payment confirmation, request attachment, subscription documents) are limited to 25 MB by default, validated against an allow-list and scanned for malware before they become available; oversize returns 413 `LP_FILE_TOO_LARGE`, wrong type 415. **[P]** (reference: 500 on oversize, no allow-list, no scan)

**A9. Audit and retention**

- BR-178: The following LP actions write an audit event in the same transaction: capital-call acknowledgement, payment-confirmation upload (with SHA-256), dealing submit (payload hash and estimate snapshot id), document view/preview/download, notice open and acknowledge, request create and reply, thread reply, colleague invite/update/revoke, bank-instruction change request, settings changes that affect security, fund switch. Investor financial artefacts are retained at least 7 years. **[I]**/[P] (reference: only document access rows and notice receipts)

**A10. Notices, requests, messages**

- BR-179: A notice targets ALL investors with a live commitment, a FUND (investors with ACTIVE or PENDING commitment in it), a SHARE CLASS (enforced), an ORG or a USER; recipients are materialised as receipts at publication; a FUND notice is never visible to an organisation without a commitment in that fund. **[P]** (reference leaks FUND notices to unscoped clients and stores but ignores share class)
- BR-180: Notice status per user is derived from that user's receipt: PUBLISHED → OPENED (first detail read) → ACKNOWLEDGED (SIGNATORY or MANAGER); organisation-level display shows the strongest status among colleagues only where the notice is addressed to the organisation; re-acknowledging does not overwrite the first timestamp. **[P]** (reference: any colleague's acknowledgement acknowledges for everyone and is overwritten on repeat)
- BR-181: A request has a reference "SR-" + 10 characters (reference) or a sequential "REQ-nnnn" in Nexus; types and priorities are closed lists; status vocabulary SUBMITTED, OPEN, ASSIGNED, UNDER_REVIEW, AWAITING_INVESTOR, AWAITING_INTERNAL, RESOLVED, CLOSED; an investor reply to a RESOLVED or CLOSED request reopens it to AWAITING_INTERNAL (the reference sets AWAITING_INVESTOR, which hands the turn back to the wrong party). **[I]**/[P]
- BR-182: Message read state is per user and per message; the unread count of the sidebar badge is the number of staff messages the current user has not read; threads are created by staff or by the investor from a record. **[P]** (reference: per message, organisation-wide, no creation path)
- BR-183: Attachments use upload-then-attach: `POST /requests/attachments` returns an id owned by the client; `attachmentIds` on create or reply must all belong to the client; unlinked uploads are purged after 24 hours. **[I]**/[P]

**A11. Colleagues and bank instructions**

- BR-184: Only a MANAGER (and staff) may invite, change or revoke colleagues; a MANAGER may grant VIEWER or SIGNATORY only; MANAGER is granted by staff; the last active MANAGER can neither be demoted nor revoked; granted `fundIds` must be a subset of the actor's own scope; revocation invalidates all of the user's sessions at once; an invitation e-mail carries a one-time activation link only (never a password) and expires after 7 days; a pending invitation shows status INVITED. **[I]**/[P] (reference: temporary password e-mailed in clear, no last-manager guard, INVITED never shown)
- BR-185: A bank-instruction change never replaces the active instruction on submission. Flow: SUBMITTED → UNDER_VERIFICATION (callback to a number on file) → APPROVED → ACTIVATED (old instruction ARCHIVED) or REJECTED; submission requires SIGNATORY or MANAGER and a verified MFA factor when `requireMfaForLp` is on; the account number is encrypted at rest and returned masked (last 4) in every response. **[I]**/[P] (reference: raw body stored and returned in clear, only SUBMITTED)

**A12. Sessions, MFA, realtime, limits**

- BR-186: `requireMfaForLp` makes enrolment mandatory at first sign-in for every LP user and adds a 5-minute step-up for bank-instruction changes and colleague changes. **[P]** (reference: challenge only for already-enrolled users)
- BR-187: The session endpoint returns `unreadCounts` {requests, messages, notices, notifications}; `notifications` = the number of items the bell can list; counts are numbers. **[I]**
- BR-188: Realtime events `lp_notification`, `lp_notice_updated`, `lp_request_created`, `lp_request_updated`, `lp_request_message`, `lp_thread_message`, `lp_thread_read`, `lp_thread_updated` are delivered to authenticated sockets only, with room joins authorised against the client; where no socket transport exists the UI polls every 30 s. **[I]**/[P] (reference: unauthenticated sockets and unauthorised detail rooms)
- BR-189: Rate limits (per user and per IP): 60 requests per minute on read routes, 20 per minute on write routes and 10 per minute on uploads and report jobs; list pages are capped at 200 rows; JSON bodies at 100 kB. **[P]** (reference: none)

##### B. Rules as implemented in the reference backend (capital, dealing, performance)

**B.1 Cross-cutting rules**


A1. Envelope. Success `{success:true, message?, data, timestamp, meta:{requestId}}`; list `{items,page,pageSize,total,totalPages}`; error `{success:false,message,error:{code,message,fieldErrors?,details?,retryable},timestamp,meta}`. `X-Request-Id` echoed if it matches `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$` else a UUID. All money = `toFixed(2)` strings (`moneyStr`); units 6 dp trimmed (`unitsStr`); NAV/unit 8 dp trimmed (`rateStr`); ratios 4 dp (`ratioStr`). Dates are `YYYY-MM-DD` strings from UTC (`dateOnly`).

A2. List query parsing (`parseListQuery`): `page>=1` default 1; `pageSize` (alias `limit`) default 50, clamp 1..200; `sortDirection|sortDir` default `desc`; `sortBy` default `createdAt` (parsed but NOT used by any capital/dealing/performance service); `fundId` = undefined when value is `"all"`; `presentationCurrency` upper-cased; `status` raw string; `from`/`to`/`asOfDate` raw strings.

A3. Fund scope. `LpUserRelation.fundIds` (Json) -> `ctx.fundScope`; empty/null = ALL funds. `assertFundAccess` throws `LP_FORBIDDEN` 403 "Not entitled to this fund". List endpoints post-filter with `fundAllowed`. Legacy path: a `Client` with `userId` and status ACTIVE and no relation row -> role VIEWER, no scope. Staff (GP admin) must pass `?clientId=`; gets `isStaff=true`, `lpRole=null`, full MANAGER permission set. Client must be `status==="ACTIVE"` else 403 "LP profile is not active" — called first in every service method.

A4. Role -> permission matrix. VIEWER: `lp.portal.access, lp.portal.switch_fund, lp.portal.view_notifications, lp.dashboard.view, lp.investments.view, lp.commitment.view, lp.capital_account.view, lp.holdings.view, lp.capital_calls.view, lp.capital_calls.download_notice, lp.distributions.view, lp.distributions.download, lp.dealing.view, lp.dealing.estimate, lp.performance.view, lp.performance.download_report, lp.activity.view, lp.activity.export, lp.documents.view, lp.documents.download, lp.notices.view, lp.requests.view, lp.messages.view, lp.organisation.view, lp.settings.view`. SIGNATORY = VIEWER + `lp.capital_calls.acknowledge, lp.capital_calls.upload_payment_confirmation, lp.dealing.subscribe, lp.dealing.redeem, lp.notices.acknowledge, lp.requests.create, lp.messages.reply, lp.settings.manage_mfa`. MANAGER = SIGNATORY + `lp.organisation.manage_colleagues`. Aliases: `LP_MANAGER`,`ADMIN`->MANAGER, `LP_VIEWER`->VIEWER. Write routes additionally wrapped in `requireLpSignatory`. Note: estimate endpoints are VIEWER-level (`lp.dealing.estimate`),.

A5. Idempotency. Header `Idempotency-Key` regex `^[\x21-\x7e]{8,200}$` else 400 `LP_VALIDATION` "Idempotency-Key header required (8–200 printable ASCII)". Scope string = `${clientId}:${action}:${METHOD}:${req.path}`; stored in `LpPortalIdempotencyKey` unique(scope, idempotencyKey). Replay (same payload hash = sha256(JSON.stringify(req.body ?? {}))) returns stored status+body with header `Idempotent-Replay: true`; different hash -> 409 `LP_IDEMPOTENCY_KEY_REUSED` "Idempotency-Key already used with a different payload". Only 2xx responses are stored, written fire-and-forget after responding. No TTL/purge found in code. Actions guarded: `capital-call-ack`, `capital-call-payment`, `subscription`, `redemption`, `perf-report-job`.
 - DEFECT (by code reading): for the two multipart routes (payment-confirmations, subscriptions) the idempotency middleware runs BEFORE `upload.single("file")`, so `req.body` is still empty when hashed -> for multipart requests the payload hash is always the hash of `{}`; same key + different file/amount replays the first response instead of 409.

A6. Upload limit: multer memory storage `fileSize 25 MB`; `maxFileMb: 25` echoed in dealing rules. No MIME whitelist and no virus scan found. `LP_FILE_TOO_LARGE`/`LP_UNSUPPORTED_MEDIA` are listed in the design SRD §22 but no code maps multer's error to them: the error handler maps only `LpPortalError` or errors with `statusCode|status`, so a multer size error would fall through to 500 `LP_EXPORT_FAILED` (inference; not tested).

A7. Audit logging: NONE found in CA/DL/PF/DB/LG (no audit write on acknowledge, payment-confirmation upload, dealing submit, report job). Only stored hashes: `LpCapitalCallPaymentConfirmation.sha256` and `LpDealingRequest.payloadHash`/`estimateSnapshotId`. the design SRD §21 requires audit events; not implemented in these services. Staff capital-call/distribution services post journal entries (see C/D) which carry `createdById`.

A8. Realtime: LP realtime events are only notices/requests/threads (contract). No event is emitted for capital calls, distributions, dealing requests, performance or jobs. No in-app notification rows are created by these flows either; `LpPortalNotificationsService.listFeed` derives bell items on read, including capital calls whose portal status is ISSUED/OVERDUE/ACKNOWLEDGED.

A9. Currency handling (as implemented).
 - Capital calls/distributions carry a `Currency` relation; portal returns `currencyCode = currency.code || "USD"`. Staff services force all eligible commitments of a fund to share ONE currency or throw. `InvestmentCommitment.currency` default "USD".
 - `LpFundMetricsService` hard-codes `currencyCode:"USD"`. Capital-call summary returns `currencyCode:"USD"` constant and sums across funds without FX.
 - Presentation currency: `presentationCurrency` query accepted only as `USD` or `ZIG` (anything else -> USD). ZIG conversion (`applyPresentationCurrency`) multiplies totalCommitment, totalPaidIn, totalDistributions, unfundedCommitment, nav by `metrics.fxRateUsdZig ?? metrics.usdZwgRate`, rounding `Math.round(n*rate*100)/100`, sets `currencyCode:"ZIG"`; if no rate: returns `{...metrics, presentationCurrency:"ZIG", fxNote:"FX rate unavailable — showing USD values"}`. Neither rate key is produced anywhere by `LpFundMetricsService`, so with current code ZIG ALWAYS falls into the "FX rate unavailable" branch. It only affects the legacy `funds[].metrics`, NOT `kpis`/`openEndedSummary` of the SRD dashboard shape. When presentation=ZIG the response also carries `exchangeRateWidget` from `ExchangeRateDisplayResolverService.resolveWidget({context:"LP_PORTAL"})`, `null` on failure.
 - Session `presentationCurrency` is hard-coded "USD". Fund-level currency: `LpFundPortalContext.currencyCode` default "USD"; `Fund.currencyCode` optional.
 - Dealing: subscription `currencyCode = (body.currency||"USD").toUpperCase` unvalidated against the fund; redemption hard-codes "USD"; holding has its own `currencyCode`. Ledger: `amount` + `currency` only — no original/reporting/FX fields, so the design SRD §11 "historical FX immutable / originalAmount / reportingAmount / exchangeRate / fxDate" is not implemented.

A10. Valuation status & as-of semantics.
 - Vocabulary in code: `FINAL` (default everywhere), plus `UNAVAILABLE` (benchmarks only). the design SRD §2.12/§5 lists ESTIMATED | PROVISIONAL | FINAL | RESTATED. `LpFundPortalContext.valuationStatus` (varchar 16, default FINAL) and `LpHoldingPosition.valuationStatus` can store any string; no code validates the set; no code sets non-FINAL values (staff counterpart not found).
 - Dashboard: `valuationStatus` = value of the LAST fund iterated that has `LpFundPortalContext.valuationStatus` (loop overwrites); `asOfDate` = today -> overwritten by the latest snapshot's `asOfDate` of the last fund -> overwritten by `portalCtx.asOfDate` when set. The requested `asOfDate` query is used only as `periodEnd` for LIVE computation; the snapshot picked is simply the latest (`orderBy asOfDate desc`, no `lte` bound) -> `asOfDate` filter does not select historical snapshots on the dashboard.
 - Session: per-fund `asOfDate = ctx.asOfDate || holding.asOfDate || today`; `valuationStatus = ctx.valuationStatus || holding.valuationStatus || "FINAL"`; `defaultAsOfDate` = max of fund as-of dates (string sort), `defaultValuationStatus` = common status if all equal else "FINAL".
 - Performance: `valuationStatus:"FINAL"` HARD-CODED for performance, history; `approvedBy:null`, `version:"1"`, `sourceModule:"LpFundMetricsService"`, `reportingCurrency:"USD"`, `calculationDate = today`. `metricsForFund` uses latest snapshot with `asOfDate <= asOf` else live compute — performance DOES honour `asOfDate`; dashboard does not.
 - Dealing overview: `asOfDate = holding.asOfDate || today`, `valuationStatus = holding.valuationStatus || "FINAL"`.

A11. Snapshot (cache) model `LpPortalMetricSnapshot` : one row per (clientId, fundId, asOfDate) unique; `metrics` Json = `LpFundMetricsSnapshot` {clientId, fundId, lpLegalName, periodStart, periodEnd, currencyCode, totalCommitment, totalPaidIn, totalCalled, totalDistributions, unfundedCommitment, nav, tvpi, dpi, rvpi, netIrr, fundName, holdingsSummary, boardExtras?}.
 - DEFECT (data contract): the DEV seed writes metrics keys `paidIn, currentNav, distributions, unfundedCommitment, netIrr, tvpi, dpi, rvpi, totalCommitment` but the dashboard/performance readers read `totalPaidIn, nav, totalDistributions, totalCalled, unfundedCommitment` — seeded snapshots therefore read as 0 for paid-in, NAV and distributions. Real (computed) snapshots use the reader's keys.

**B.2 KPI definitions (where computed / stored)**


All per (client, fund) in `LpFundMetricsService.computeForClient`, then summed in DB/PF:
B1. Total commitment = sum of `InvestmentCommitment.amount` for the client+fund with status in (ACTIVE, PENDING). Stored: `investment_commitments.amount` (Decimal 15,2), unique(clientId,fundId).
B2. Paid-in (`totalPaidIn`) = sum of `CapitalCallAllocation.amountPaid` over the client's active commitments, ALL calls regardless of status. Stored: allocation roll-up of append-only `CapitalCallAllocationPayment` rows.
B3. Called (`totalCalled`) in the fund metrics service = sum of `currentCallAmount` for allocations whose call status NOT IN (CANCELLED, DRAFT) — includes un-noticed (INITIATED) calls. The portal dashboard OVERRIDES this: `called` = sum of `currentCallAmount` over allocations whose call passes `isCapitalCallVisible` (see C1) — "what the investor can actually see".
B4. Unfunded commitment = `max(0, totalCommitment − called)` — "Commitment minus CALLED, not paid-in" (the design SRD §2.6). In the dashboard `unfunded` is recomputed on the visible-called basis and `totalCommitment` is summed from snapshots.
B5. Outstanding called = `max(0, called − paidIn)` where `called` is live (visible basis) but `paidIn` comes from the (possibly stale) snapshot -> can be wrong between snapshot refreshes (see snapshot cron below: capital-call payment recording does not refresh LP snapshots).
B6. Paid-in + outstanding + unfunded = commitment is the stated identity (comment) — true only when snapshot paid-in is fresh.
B7. NAV (live compute) = `fundNav × lpShare` where `fundNav = totalInvested × (1 + portfolioRoi)` if `portfolioRoi != null && totalInvested>0` else `totalInvested`; `lpShare = LP paidIn / fundDashboard.performanceOverview.paidIn` (0 if denominator 0). NOTE: `performanceOverview.paidIn` is actually the SUM of `Fund.totalAmount` (fund size, not paid-in); `totalInvested` = sum of disbursements to portfolio companies; `portfolioRoi = (totalValue − totalInvested)/totalInvested`. NAV is therefore an approximation, not an approved valuation.
B7b. Distributions (`totalDistributions`) = sum of `DistributionAllocation.amountPaid` for distributions with status != CANCELLED — PAID-OUT amounts, not declared.
B8. TVPI = `(distributions + nav) / paidIn`, DPI = `distributions / paidIn`, RVPI = `nav / paidIn`; all 0 when paidIn <= 0 (matches the design SRD §13). Dashboard/performance re-derive consolidated multiples from summed aggregates if `paidIn>0`, else keep the last fund's.
B9. Net IRR = `fundDashboard.metrics.lpNetIRR ?? null` where `lpNetIRR = fundGrossIRR − 0.02*100` i.e. gross fund XIRR% minus a hard-coded 2 percentage points, clamped at −100 before subtraction. It is a FUND-level percent number (e.g. 16.7), not an LP-level fraction. Seeded snapshots store a fraction (0.187). The portal prints `ratioStr(netIrr,4)` without unit conversion => unit inconsistency (percent for live compute, fraction for seed) — flag for SRD: "decide percent vs fraction".
 - With several funds, `netIrr` = the LAST fund with non-null netIrr (not weighted).
B11. `investmentCount` = count of the client's commitments (ACTIVE/PENDING) in the selected funds; `portfolioCompanyCount` = non-EXITED portfolio companies in those funds. the design SRD example had.
B12. Open-ended summary : over ALL active `LpHoldingPosition` rows (selected fund or all entitled funds): `accountValue = Σ accountValue`, `unitsHeld = Σ units` (units of different share classes/funds summed), `navPerUnit` = last non-zero `navPerUnit` in iteration order, or `accountValue/unitsHeld` if all zero; `ytdReturn = navPerUnit(now)/navPerUnit(earlier) − 1` where `earlier` = latest `LpHoldingPosition` row for `holdings[0].fundId` with `asOfDate <= Jan 1 (UTC) of as-of year` (falls back to current NAV -> 0). Because `LpHoldingPosition` has unique(clientId,fundId,shareClass) only ONE row exists per share class, so `earlier` can only be that same row => `ytdReturn` is effectively always 0 and `openEndedHistory.points` (last 24 rows asc `asOfDate<=asOf` for the target fund = OPEN_ENDED fund if any else first fund) has at most one point per share class. Strings: units `String(number)`, nav `String(number)`.
 - PF `openEndedMetrics.ytdReturn = ratioStr(Number(accountValue)>0 ? 0 : 0, 4)` = hard-coded "0.0000". `navPerUnit/unitsHeld/accountValue` from latest active holding of the FIRST open-ended fund.
B13. the design SRD §13 open-ended returns (1M/3M/YTD/1Y/SI; NAV return = end/begin − 1) — not implemented beyond the placeholder above. the design SRD §2.5 "never substitute fund AUM for investor NAV" — code uses LP paid-in/fund size share (B7) or holding `accountValue`.

**B.3 Capital calls (investor view)**


C1. Visibility (`isCapitalCallVisible`): hidden if header status is DRAFT or CANCELLED; visible if `noticesSentAt != null`; else visible only when status in {NOTICES_SENT, ISSUED, ACTIVE, PARTIALLY_PAID, PAID, CLOSED}. Staff services only produce INITIATED -> NOTICES_SENT -> PARTIALLY_PAID -> FULLY_PAID (schema comment default INITIATED). Consequences: INITIATED (not noticed) = hidden; `FULLY_PAID` header is NOT in the visible set (only visible if `noticesSentAt` is set, which "send notices" sets); ISSUED/ACTIVE/PAID/CLOSED/DRAFT/CANCELLED are never written by the staff service read (not found in code).
C2. Allocation = one row per LP per call (`CapitalCallAllocation`): `currentCallAmount`, `amountPaid`, `status` PENDING|PARTIALLY_PAID|PAID. Staff allocation maths : per eligible commitment (status ACTIVE/PENDING): `uncalledBefore = round2(commitment − Σprior currentCallAmount)`; skip if <=0; `rawCall = round2(commitment × callPercent / 100)`; `callAmount = min(rawCall, uncalledBefore)`; skip if <=0. i.e. PRO-RATA BY COMMITMENT, capped at remaining uncalled. `round2` = HALF_UP. `callPercent` must be 0 < p <= 100 else "callPercent must be a number between 0 and 100 (e.g. 10 for 10%)". Allocation snapshots stored: `lpLegalNameSnapshot, totalCommitmentSnapshot, uncalledCapitalBeforeSnapshot`.
C3. Portal status (`mapPortalCallStatus`), evaluated in this precedence: (1) header CANCELLED -> CANCELLED; (2) `amount>0 && paid>=amount` -> PAID; (3) `paid>0` -> PARTIALLY_PAID; (4) `portalState.acknowledgedAt` set -> ACKNOWLEDGED; (5) `dueDate < todayUTC(date-only string compare) && paid<amount` -> OVERDUE; (6) else ISSUED. Hence an ACKNOWLEDGED call that is past due still reads ACKNOWLEDGED (never OVERDUE), so it is excluded from `overdue` KPI and dashboard HIGH severity. Portal vocabulary: ISSUED, ACKNOWLEDGED, PARTIALLY_PAID, PAID, OVERDUE, CANCELLED (the design SRD §9 additionally lists DRAFT hidden).
C4. Summary item fields (`mapCallSummary`): `id`=allocation id; `callNo`; `fundId`,`fundName`; `issueDate = noticesSentAt || transactionDate`; `dueDate = paymentDueDate`; `currencyCode`; `amount, paid, outstanding = max(0, amount − paid)`; `status`; `acknowledgedAt`. `callNo` (`deriveCallNo`) = `cc.callNumber` if present (the `CapitalCall` model has NO `callNumber` column, => never) else `Number("MMDD" of transactionDate)` (e.g. 2026-09-04 -> 904) else last 4 chars of id uppercased. Not a sequential call number (the design SRD example "7").
C5. List (`listCapitalCalls`): allocations of the client, optionally `fundId`, `createdAt desc`; filter fundAllowed + visible; optional `status` (uppercased, matched on the derived portal status); in-memory paging; `total = items.length`. Capital-call list has no `from/to`, `search`, `sortBy` support.
C6. Detail (`mapCallDetail`): summary + `wiring` + `timeline`. Wiring parsed from `CapitalCall.bankInstructions` (free text; if JSON: `bankName|bank_name, accountName|account_name, accountNumber|account_number, accountNumberMasked (else "••••"+last4), abaRouting|routing|swift, reference`); non-JSON -> only `raw`. `wiring.reference` fallback `"${fundName||"Fund"} Call ${callNo} – Investor"`. NOTE: full `accountNumber` from the JSON is returned unmasked alongside the masked one. Timeline codes (fixed 4): `ISSUED` (completed always true; at = noticesSentAt||transactionDate), `ACKNOWLEDGED` (at/completed from portal state), `PAYMENT_RECEIVED` (completed = paid>0; at = last payment `recordedAt`), `CLOSED` (completed = paid>=amount && amount>0; at = last payment time).
C7. Due-soon / overdue / open definitions (summary; items limited to first 200): 
 - `openCount` = count of statuses in {ISSUED, ACKNOWLEDGED, PARTIALLY_PAID, OVERDUE}; `outstanding` = Σ `outstanding` of those; `overdue` = Σ outstanding of status OVERDUE only.
 - `dueSoon`: `dueDate >= today && dueDate <= today+14 days` and `status !== "PAID"` (so CANCELLED/PAID excluded only for PAID; window constant 14 days).
 - `paidCallCount` = count of status PAID; `paidYtd` = Σ `paid` of PAID calls whose `dueDate` string starts with the current (server-local) year — keyed by DUE year not payment date; partial payments ignored.
 - Returned: `{openCount, outstanding, overdue, paidYtd, paidCallCount, dueSoonCount, dueSoonAmount, totalDistributions, upcomingDistributionNotices:{count,amount}, currencyCode:"USD"}`.
 - **DEF-454** `totalDistributions` and `upcomingDistributionNotices` read `d.amount` and statuses DECLARED/NOTIFIED/ISSUED but distribution items expose `gross/netPaid` (no `amount`) and statuses PENDING/PARTIALLY_PAID/PAID -> both are always 0.
 - Amounts summed across currencies/funds without FX; output labelled USD.
C8. Acknowledge (`acknowledge`; route, perm `lp.capital_calls.acknowledge`, SIGNATORY+, Idempotency-Key required): checks active client, allocation owned by client (else 404 `LP_NOT_FOUND` "Capital call not found"), fund allowed, call visible (else 404). Errors: derived status CANCELLED -> 409 `LP_CALL_NOT_ISSUED` "Capital call is cancelled"; not visible -> 409 `LP_CALL_NOT_ISSUED` "Capital call is not issued"; already acknowledged -> 409 `LP_CALL_ALREADY_ACKNOWLEDGED` "Already acknowledged". Effect: upsert `LpCapitalCallPortalState` {capitalCallAllocationId (unique), clientId, acknowledgedAt=now, acknowledgedById=userId}; response `{acknowledgedAt}` with message "Capital call acknowledged". Never touches `amountPaid`/`status`. Allowed even when the call is already PAID (not blocked). No audit/realtime/notification (A7/A8).
C9. Payment confirmation (`uploadPaymentConfirmation`; route, perm `lp.capital_calls.upload_payment_confirmation`, SIGNATORY+): multipart field `file` (required, else 400 `LP_VALIDATION` "file is required"), optional body `amountClaimed`, `notes`. Checks allocation ownership/scope/visibility only (no status check, no upload when cancelled check). Stores file to `<cwd>/uploads/lp-portal/payment-confirmations/<allocationId>/<Date.now>_<name with [^\w.\-]+ -> _>`, computes sha256, creates `LpCapitalCallPaymentConfirmation` {fileName, mimeType (multer value or application/octet-stream), storagePath (relative), sha256, amountClaimed (Number; not validated -> NaN possible), notes, uploadedById}. Response 201 `{id,fileName,sha256,amountClaimed,uploadedAt}` message "Payment confirmation uploaded". Effect on `paid`: NONE — `amountPaid` only changes when staff records a payment. No code in the repo reads `LpCapitalCallPaymentConfirmation` (only the portal write path) => no staff review/approval of confirmations exists (not found in code).
C10. Notice download (`downloadNotice`; perm `lp.capital_calls.download_notice`): returns a `.txt` stub (`capital-call-<callNo>-notice.txt`, `text/plain`) with lines: CAPITAL CALL NOTICE / Fund / Call # / Issue Date / Due Date / Amount / Outstanding / Status / "Wiring instructions:" (raw or joined fields or "(see fund administrator)") / "This is an investor notice stub. Final PDF may be attached via Document Centre." Not a PDF. (Staff notices ARE PDFs, emailed to investors.)
C11. Linked documents (`listCallDocuments`): `LpPortalDocument` rows for the client with `sourceType in ("CAPITAL_CALL","CAPITAL_CALL_ALLOCATION")` and `sourceRefId = allocationId`; `{id,name=title,category,publishedDate,checksumSha256,status: publishedAt?"PUBLISHED":"DRAFT"}`.
C12. Header and allocation status maths (staff side, drives portal): allocation `PENDING (paid<=0) | PARTIALLY_PAID | PAID (paid>=call)`; header recompute : all PAID -> `FULLY_PAID`; any partial/paid -> `PARTIALLY_PAID`; else `NOTICES_SENT` if noticesSentAt else `INITIATED`. Payment must be >0, <= remaining, rounded HALF_UP.

**B.4 Distributions (investor view)**


D1. Source of truth: `Distribution` header + `DistributionAllocation` per LP. Types stored in `Distribution.source`: DIVIDEND | EXIT_PROCEEDS | REALISATION_PROCEEDS(alias) | INTEREST | INCOME | RETURN_OF_CAPITAL | OTHER. Portal `type` map (`mapDistributionType`): EXIT_PROCEEDS|REALISATION_PROCEEDS -> `REALISATION_PROCEEDS`; DIVIDEND/INTEREST/INCOME/RETURN_OF_CAPITAL pass through; anything else (incl. OTHER) -> that uppercased value or "OTHER". NOTE: staff create stores the alias `REALISATION_PROCEEDS` as is (no normalisation to EXIT_PROCEEDS in the distribution service) though the schema comment lists only DIVIDEND|EXIT_PROCEEDS|INTEREST|OTHER.
D2. Visibility (`isDistributionVisible`): everything except status DRAFT/CANCELLED — i.e. a freshly DECLARED distribution (before notices) IS visible, unlike capital calls.
D3. Staff split maths : waterfall (`computeWaterfall`): `gross`; if `carryRate` (fund.carryRate or override, must be in [0,1]) >0: `hurdleApplied = round2(gross × hurdleRate)` only when `hurdleType === "PREFERRED_RETURN"` (a crude approximation, capped at gross); `carry = round2((gross − hurdleApplied) × carryRate)` capped; `netToLPs = round2(gross − carry)`; must be >0. Split `netToLPs` pro-rata by `paidIn` (Σ amountPaid on commitments), or by commitment when total paid-in is 0; each share `round2(netToLPs × weight / splitTotal)`, last LP takes the remainder. Stored: `grossAmount, carryAmount, netToLPs, hurdleAppliedAmount`, allocation `paidInSnapshot, commitmentSnapshot, shareAmount (net of carry), amountPaid=0, status PENDING`.
D3b. Journal on declare: Dr (income account by source: DIVIDEND 4100, INTEREST 4110, EXIT_PROCEEDS/REALISATION_PROCEEDS 4120, INCOME/OTHER 4130, RETURN_OF_CAPITAL 3020 equity) = gross; Cr 2400 Distributions Payable = netToLPs; Cr 4020 Performance fee revenue = carry. Payout: Dr 2400 / Cr cash GL. Cash GL resolution: explicit id -> env `CAPITAL_CALL_RECEIPT_CASH_ACCOUNT_NO` -> first active bank with GL -> account 1100/Bank/Cash.
D4. Portal item (`mapDistSummary`): `id` = allocation id; `reference = "DIST-" + last 6 chars of allocation id, uppercased`; `paymentDate = distribution.distributionDate`; `gross = shareAmount` (the LP's NET-of-carry share, not fund gross); `netPaid = Number(amountPaid) || gross` (falls back to gross when nothing paid yet); `adjustments = max(0, gross − netPaid)` => for a part-paid allocation `adjustments` equals the UNPAID remainder (not fees/withholding); 0 when unpaid or fully paid; `status` = ALLOCATION status uppercased (PENDING | PARTIALLY_PAID | PAID); `destinationBankMasked` = `"<bankName> <accountNumberMasked>"` of the client's ACTIVE `LpBankAccount` for that fund else the fund-agnostic (fundId null) account, ordered by `isDefault desc, updatedAt desc`; `documentId` always null; `currencyCode`. The the design SRD example (gross 500000, adjustments 10000, netPaid 490000) is NOT reproducible from stored data (no withholding/adjustment field exists).
D5. List filters : `fundId`, `from`/`to` on `paymentDate` (rows with null date always pass), in-memory pagination; no `type`/`status`/`search` filter; allocation `createdAt desc`.
D6. Downloads: per-distribution `.txt` (`distribution-<reference>.txt`; lines DISTRIBUTION NOTICE / Reference / Fund (prints fund ID, not name) / Payment Date / Type / Gross / Net Paid / Status); statement `.txt` (`distribution-statement-<asOf>.txt`; lines `id\tdistributionDate\tgrossAmount||shareAmount\tstatus` but those fields do not exist on items => blank columns; `asOfDate` is only used for the filename/header, not as a filter). Perms `lp.distributions.view|download` (VIEWER+).

##### C. Rules as implemented in the reference backend (documents, notices, requests, messages, organisation, settings, session)

**C.1 Cross-cutting (auth, envelopes, roles, idempotency)**


1. **Mount and auth.** Router mounted at `/api/lp-portal`. `router.use(authenticate)` then `router.use(lpPortalContract)`. `authenticate` verifies a Bearer JWT, loads the user, checks user availability window and compares `tokenVersion` claim with DB `tokenVersion`, else 401 "Unauthorized". JWT is signed with `expiresIn: "7d"` and an `aud` equal to the portal; the LP routes do NOT check `aud` (not found in code), so a staff JWT works on LP routes with `?clientId=`.
2. **Access resolution** (`requireLpPortalAccess`, +): (a) GP staff or sysadmin (`isGpStaff`/`isSysAdmin`) MUST pass `?clientId=`, else 400 "GP staff must pass ?clientId= for LP portal impersonation"; (b) otherwise the first ACTIVE `LpUserRelation` for the user ordered by `createdAt asc` is used - there is NO multi-organisation switching; (c) fallback "legacy client": a `Client` whose `userId` is the user and `status = ACTIVE` gives role VIEWER and no fund scope; (d) staff with `staffClientId` and no relation gets `{isStaff:true, lpRole:null}`; (e) else 401 "No active LP portal access". Staff GP role codes: `admin`, `fund_manager`, `cfo`, `FUND_MGR`, `CFO`; LP role codes `LIMITED_PARTNER`, `LP_VIEWER`, `LP_INSTITUTIONAL_MANAGER`.
3. **Client must be ACTIVE.** Nearly every service method first calls `assertClientActive` -> 404 "LP profile not found" or 403 "LP profile is not active" when `Client.status !== "ACTIVE"`. `Client.status` default "ACTIVE" (Client model).
4. **Roles.** `VIEWER | SIGNATORY | MANAGER`; aliases `LP_MANAGER`, `ADMIN` -> MANAGER, `LP_VIEWER` -> VIEWER. `normalizeLpRole` returns the upper-cased raw string for ANY unknown value instead of rejecting it (: `ROLE_ALIASES[key] || key`), so an invite/patch with `role:"FOO"` is persisted as "FOO" (VarChar(16)) and then treated as no permissions beyond VIEWER defaults in `permissionsForRole`.
5. **Permission matrix**. VIEWER: `lp.portal.access, lp.portal.switch_fund, lp.portal.view_notifications, lp.dashboard.view, lp.investments.view, lp.commitment.view, lp.capital_account.view, lp.holdings.view, lp.capital_calls.view, lp.capital_calls.download_notice, lp.distributions.view, lp.distributions.download, lp.dealing.view, lp.dealing.estimate, lp.performance.view, lp.performance.download_report, lp.activity.view, lp.activity.export, lp.documents.view, lp.documents.download, lp.notices.view, lp.requests.view, lp.messages.view, lp.organisation.view, lp.settings.view`. SIGNATORY = VIEWER + `lp.capital_calls.acknowledge, lp.capital_calls.upload_payment_confirmation, lp.dealing.subscribe, lp.dealing.redeem, lp.notices.acknowledge, lp.requests.create, lp.messages.reply, lp.settings.manage_mfa`. MANAGER = SIGNATORY + `lp.organisation.manage_colleagues`. Staff impersonation gets the MANAGER set. `lp.settings.manage_mfa` is defined but no route checks it (not found in code).
6. **Two-layer gating on routes.** Write routes chain `requireLpPortalAccess` + `requireLpSignatory` (SIGNATORY, MANAGER or staff; 403 "Authorised Signatory access required") + `requireLpPermission(code)` (403 "Missing permission {code}"). Colleague routes chain `requireLpManager` (403 "LP Manager access required"). Admin routes use `requireGpAdmin` (403 "GP Ops access required"); MFA policy routes use `requireSysAdmin` (role code `admin` only, 403 "SysAdmin access required", +).
7. **Envelopes.** Success `{success:true, [message], data, timestamp, meta:{requestId}}`; money/BigInt/Decimal -> strings via `decimalSafe`. List `data:{items,page,pageSize,total,totalPages}`. Error `{success:false, message, error:{code,message,[fieldErrors],[details],retryable}, timestamp, meta}`. `X-Request-Id` echoed if it matches `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$` else a UUID. Error mapping: `LpPortalError` as-is; any error with `status/statusCode` -> 401 `LP_UNAUTHORIZED`, 403 `LP_FORBIDDEN`, 404 `LP_NOT_FOUND`, anything else `LP_VALIDATION` with that status; unhandled -> 500 `LP_EXPORT_FAILED` with the raw `err.message`. Consequence: a multer "File too large" error (no `status`) falls into the 500 branch, NOT `413 LP_FILE_TOO_LARGE` as the SRD requires.
8. **List query parsing** (`parseListQuery`): `page` default 1 (>=1); `pageSize` = `pageSize` ?? `limit`, default **50**, clamped 1..200; `sortDirection|sortDir` default desc; `search` trimmed; `fundId` ignored when the literal string `all`; `status` passed raw; `presentationCurrency` upper-cased. Controllers use `listBody(items,page,pageSize,total)`.
9. **Idempotency.** Header `Idempotency-Key` must match `^[\x21-\x7e]{8,200}$` else 400 `LP_VALIDATION` "Idempotency-Key header required (8-200 printable ASCII)". Scope = `{clientId}:{action}:{method}:{path}`; store = `LpPortalIdempotencyKey` unique(scope, key) with `payloadHash` = sha256(JSON body). Same key + same hash -> replay stored status/body with header `Idempotent-Replay: true`; different hash -> 409 `LP_IDEMPOTENCY_KEY_REUSED` "Idempotency-Key already used with a different payload". Only 2xx responses are stored, and the store is fire-and-forget. Required on: `POST /notices/:id/acknowledge` (action `notice-ack`, :267-273), `POST /requests` (`service-request`, :296-302), `POST /bank-instructions/changes` (`bank-instruction-change`, :343-349), `POST /colleagues` (`invite-colleague`, :362-368). NOT required on: `POST /requests/attachments`, `POST /requests/:reference/messages`, `POST /messages/:id/replies`, `POST /messages/:id/read`, `PATCH /colleagues/*`, `PATCH /settings/*`. (The SRD, lists "create request, acknowledge notice, invite colleague" - code additionally requires it for bank-instruction changes)
10. **Fund scoping.** `ctx.fundScope` = `LpUserRelation.fundIds` (JSON array) when non-empty else `null`. `fundAllowed` returns **true when `fundScope` is null/empty**, i.e. null means "all funds", it does NOT mean "only funds the client has committed to". `assertFundAccess` throws 403 `LP_FORBIDDEN` "Not entitled to this fund".

**C.2 Documents / vault**


11. **Document entity** = `LpPortalDocument` : `clientId`, `fundId?`, `category VarChar(32)` (free string), `title VarChar(512)`, `fileUrl?`, `storagePath?`, `sha256?`, `mimeType?`, `fileSizeBytes?`, `pageCount?`, `publishedAt?`, `publishedById?`, `sourceType VarChar(32)`, `sourceRefId?`. Visibility is by `clientId` (the investor organisation), then fund filter: rows with `fundId` null are visible to all org users; rows with a `fundId` are hidden when `fundScope` excludes it.
12. **Category vocabulary actually written by code:** `PERFORMANCE_REPORT` (fund-report delivery sync), `QUARTERLY_STATEMENT`, `TAX`, `MANUAL` (default for admin upload). No enum validation: an admin upload accepts any string. The Nexus UI union is `TAX | AUDIT | PERFORMANCE_REPORT | CALL_NOTICE | MANUAL | QUARTERLY_STATEMENT | LEGAL`; `AUDIT`, `CALL_NOTICE`, `LEGAL` are not written by any code read here (not found in code). The SRD list `STATEMENTS, CAPITAL_CALLS, DISTRIBUTIONS, FUND_REPORTS, TAX, LEGAL, GOVERNANCE, NOTICES, SUBSCRIPTION, REDEMPTION, OTHER` is NOT what the code emits.
13. **`sourceType` vocabulary:** `GP_UPLOAD` (default), `FUND_REPORT_SYNC`, `QUARTERLY_STATEMENT_SYNC` (QuarterlyStatementPublishService:30), `TAX_RETURN_PACK_SYNC`. `sourceRefId` = report job id / quarterly recipient id / tax pack id.
14. **Publication.** `publishDocument` always sets `publishedAt = now`. Therefore mapped `status` (`publishedAt ? "PUBLISHED" : "DRAFT"`) is always PUBLISHED; `DRAFT` is unreachable through code. SRD statuses `REQUIRES_SIGNATURE`, `SUPERSEDED`, `RESTATED`, `WITHDRAWN` are not implemented (not found in code). There is no update, withdraw, supersede or delete path for a document.
15. **Document API shape** (`mapDoc`): `id, name(=title), fundId, fundName, category, period (always null), publishedDate (YYYY-MM-DD from publishedAt), version (hard-coded "1.0"), status, accessScope (hard-coded "INVESTOR_ORGANISATION"), checksumSha256 (=sha256), mimeType (db value or "application/pdf"), fileSizeBytes (number|null), pageCount, permissions (hard-coded ["VIEW","DOWNLOAD"]), sourceType, sourceRefId`. `mimeType`, `fileSizeBytes`, `pageCount` are never written by any publisher (does not set them) so they are always null/defaulted; `period` and `version` are not stored anywhere.
16. **List** `GET /documents` (perm `lp.documents.view`): filters `clientId`, `fundId` (unless "all"), `category` exact, search = `search` or `q` -> `title contains`. Order `publishedAt desc`. Fund-scope filtering and pagination are done IN MEMORY after fetching all rows, `total` = filtered count. Response items = `mapDoc`.
17. **Detail** `GET /documents/:id`: loads doc (404 "Document not found" if `clientId` differs or fund not allowed), writes audit `VIEW`, returns `mapDoc` plus `history` = last 20 audit rows (`createdAt desc`) as `{user: userId (raw id, not a name), action, at, ip}`. The audit history is client-wide (all users of the organisation), not per user.
18. **Audit log** = `LpDocumentAccessAudit`: `documentId, clientId, userId?, action VarChar(16) VIEW|DOWNLOAD|PREVIEW, ipAddress, userAgent, createdAt`. Written with `req.ip` and the `user-agent` header. Written AFTER the file was successfully fetched for download/preview, so failed downloads are not audited. Not audited: the `GET /vault` list, `verify`, and the legacy `GET /reports/:jobId/download`. No other LP action is written to the system audit log - `AuditService` is not referenced anywhere under `services/lpPortal` or in `LpPortalController` (grep, no matches). Immutability: the application blocks writes to audit URL paths only; the table has no update/delete route.
19. **Download.** `GET /documents/:id/download` (perm `lp.documents.download`): server-streams the file (no signed URL, no expiry, no per-user or per-IP rate limit - not found in code). Source: local `storagePath` if the file exists on disk else `RemoteUploadService.downloadFile(fileUrl||storagePath)`. Filename = `title.replace(/[^\w.-]+/g,"-") + ext`; `ext` is derived from `doc.mimeType` (`pdf`->.pdf, `spreadsheet`->.xlsx, `word`->.docx, else `.bin`). Because `mimeType` is never stored, every real download is named `*.bin` (DEFECT). Content-Type = `doc.mimeType || "application/pdf"`. 404 "File not available" when neither `fileUrl` nor `storagePath`. Header `Content-Disposition: attachment; filename="..."`.
20. **Vault download alias** `GET /vault/:documentId/download` hard-codes `Content-Type: application/pdf` and also audits `DOWNLOAD` (it calls `LpPortalDocumentsService.download`).
21. **Preview** `GET /documents/:id/preview` (perm `lp.documents.view`): allowed only if `mimeType` (default "application/pdf") is `application/pdf` or starts with `image/`, else 415 `LP_UNSUPPORTED_MEDIA` "Preview is only available for PDF and image documents" with `details:{mimeType}`. Since stored mimeType is always null the 415 can never fire for real data; any file (e.g. a.docx admin upload) is previewed as application/pdf (DEFECT). Audits `PREVIEW`; response `Content-Disposition: inline`.
22. **Vault verification (sha256).** `GET /vault/:documentId/verify` (perm `lp.documents.view`, any role): if no `sha256` -> `{documentId, verified:false, reason:"No checksum on file"}`; else downloads the full file, computes sha256 hex, returns `{documentId, verified: hash===sha256, expectedSha256, actualSha256}`. No audit row. Checksum is set at publish time: admin upload computes sha256 over the uploaded buffer, quarterly statements/tax packs pass the generator's sha256, performance reports copy `FundReportRecipientJob.pdfSha256`.
23. **Vault list** `GET /vault` (perm `lp.documents.view`): query `category`, `search`, `fundId` read raw from `req.query`; NO pagination, NO `all` handling (so `fundId=all` matches nothing), no `assertFundAccess`; row = `{documentId, category, title, fundId, fundName, publishedAt, sourceType, sha256}`; response data is a bare array.
24. **Summary / KPI definitions** `GET /documents/summary` :
 - `total` = count of visible documents (client + fund scope).
 - `newThisWeek` = visible docs with `publishedAt >= now - 7 days` (`setDate(getDate-7)`, server local time).
 - `requiresSignature` = **hard-coded 0**. No signature workflow exists (not found in code).
 - `secureDownloadsYtd` = count of `LpDocumentAccessAudit` rows for the client with `action = "DOWNLOAD"` and `createdAt >= 1 Jan of the current year` (server local time). It counts all users of the organisation and is not fund-scope filtered. PREVIEW/VIEW are not counted.
 - `byCategory` = `[{category,count}]` over visible docs, insertion order of first appearance.
25. **Publishing sources (staff/system side):** (a) `POST /admin/documents` multipart `file` + body `clientId, fundId?, category (default "MANUAL"), title (default original filename)`, gate `requireGpAdmin`, multer memory storage `limits.fileSize = 25 MB` and NO mime filter; service computes sha256, uploads to remote storage folder `lp-portal-vault` via `remoteUploadService.uploadSingleFile`, filename extension from a map of 9 mimes (`pdf, txt, csv, png, jpg, docx, xlsx, doc, xls`, else `bin`); `clientId` is not validated (an unknown id fails on FK); status 201. (b) auto-index of a DELIVERED performance-report job: title `"{fund} — Performance Report ({periodEnd yyyy-mm-dd})"`, category PERFORMANCE_REPORT, idempotent per `(FUND_REPORT_SYNC, jobId)` (called by the fund-report run orchestrator). (c) quarterly statement publish: title `"{fund} — Quarterly Statement ({periodEnd})"` (QuarterlyStatementPublishService:20-32) and upserts `LpPortalMetricSnapshot`. (d) tax return pack: title `"{entity} — Tax Return {period} {year}"`, delivered ONLY to the earliest ACTIVE/PENDING commitment client of the fund - a fund with several investors gets it for one only (DEFECT/limitation).
26. **No notification on publish.** Publishing a document sends no email, no `lp_notification`, no realtime event and creates no notice (not found in code). The `emailDocuments`/`inAppDocuments` preference flags exist but nothing reads them (see rule 70).
27. **Legacy reports** `GET /reports`, `GET /reports/:jobId/download` (perms `lp.documents.view/download`) are the old report list (out of scope here).

**C.3 Notices**


28. **Entity** `LpNotice` : `title VarChar(512), body Text, category? VarChar(32), status VarChar(32) default "PUBLISHED", targetType VarChar(32) default "ALL" (ALL|FUND|ORG|USER), fundId?, clientId?, userId?, shareClass? VarChar(64), publishedAt?`. Receipt `LpNoticeReceipt` (5131-5145): `noticeId, clientId, userId?, openedAt?, acknowledgedAt?` unique(noticeId, clientId, userId).
29. **Stored status is only `PUBLISHED`**. `DELIVERED`, `OPENED`, `ACKNOWLEDGED` are derived: LP-facing `status` = `ACKNOWLEDGED` if any receipt of the client has `acknowledgedAt`, else `OPENED` if any receipt has `openedAt`, else the stored status. Draft/scheduled/withdrawn/expired states do not exist (not found in code). Lists accept stored status `PUBLISHED` or `DELIVERED`, but the session unread count counts only `PUBLISHED` - inconsistent.
30. **Category / kind.** `category` = stored value or, when null, inferred from the title (lower-cased): contains "capital call" or "call #" -> `CAPITAL_CALL`; contains "report", "letter" or "quarterly" -> `REPORT`; contains "policy" or "terms" -> `POLICY`; else `GENERAL`. `kind` is always identical to `category`. Staff may set `category` to any string up to 32 chars (no enum).
31. **Targeting.** `targetType`: `ALL` (every client with a live commitment), `FUND` (clients with ACTIVE/PENDING `InvestmentCommitment` on `fundId`), `ORG` (one client, `clientId` required), `USER` (one client + `userId`; `clientId` required). Validation errors (HTTP 400, plain messages): "title is required", "body is required", "targetType must be one of: ALL, FUND, ORG, USER", "fundId is required when targetType is FUND", "clientId is required when targetType is ORG or USER".
32. **Visibility for the LP** (`noticeVisible`, + list query): the DB query returns notices with status PUBLISHED/DELIVERED and (`ALL`) or (`ORG` and `clientId = mine`) or (`USER` and `userId = mine`) or (`FUND`); then an in-memory filter drops a notice if `clientId` is set and differs, `userId` set and differs from the caller, or `fundId` set and not `fundAllowed`. **Share class is stored and returned but NEVER used for visibility** (do not reference `shareClass`) - share-class targeting is not enforced. **FUND notices are visible to every client whose `fundScope` is null** (rule 10), including clients with no commitment in that fund - only the receipt materialisation (rule 33) uses commitments (**DEF-455** cross-investor leakage). The list ignores a `fundId` query param.
33. **Staff create** `POST /admin/notices` (gate `requireGpAdmin`): creates the notice with `status "PUBLISHED"` and `publishedAt = now`, then materialises one `LpNoticeReceipt` (userId = the notice's `userId` or null, `openedAt/acknowledgedAt` null) per recipient client via `createMany skipDuplicates`. Response 201 = `getById` with counters. No email, no realtime event, no `lp_notification` is emitted (`publishNoticeRealtime` exists at but has no caller - not found in code). No edit, delete, recall, expiry or scheduling endpoint exists.
34. **Staff list/counters** `GET /admin/notices?page&pageSize` (default 50, max 200, `createdAt desc`) returns `{id,title,category,status,targetType,fundName,publishedAt,delivered,opened,acknowledged}` where each counter is the number of DISTINCT `clientId` among receipts (`delivered` = any receipt, `opened` = openedAt not null, `acknowledged` = acknowledgedAt not null). Counting distinct clients is deliberate because delivery receipts have `userId null` while open/ack receipts are per person. There is NO `GET /admin/notices/:id` route although `getById` exists (only used after create).
35. **LP list** `GET /notices?page&pageSize` (perm `lp.notices.view`): items `{id,title,category,kind,status,fundId,fundName,shareClass,requiresAcknowledgement (hard-coded true),publishedAt,acknowledgedAt,preview (first 240 chars of body)}`, sorted `publishedAt desc`, in-memory pagination, `total` = visible count. The receipt used for status is looked up by `clientId` only, so acknowledgement/opening by ANY colleague marks the notice ACKNOWLEDGED/OPENED for every colleague in the list.
36. **Open semantics.** `GET /notices/:id` (perm `lp.notices.view`, any role) has a write side effect: if the caller has no receipt (matched on `noticeId + clientId + userId`) one is created with `openedAt = now`; if a receipt exists with no `openedAt` it is set; in both cases `lp_notice_updated {status:"OPENED"}` is emitted. Detail returns list fields plus `body` and `openedAt`; 404 `LP_NOT_FOUND` "Notice not found" when invisible.
37. **Acknowledge.** `POST /notices/:id/acknowledge` (SIGNATORY/MANAGER only, perm `lp.notices.acknowledge`, Idempotency-Key required): find the receipt for `(notice, client, userId)`; update `openedAt = existing.openedAt || now`, `acknowledgedAt = now` or create a receipt with both = now. Re-acknowledging OVERWRITES `acknowledgedAt` (**DEF-456** original timestamp lost; only the idempotency key protects replays). Response 200, message "Notice acknowledged", data `{acknowledgedAt}`. Emits `lp_notice_updated {status:"ACKNOWLEDGED"}`. Acknowledgement is per person (receipt per user) but ALL status displays and unread counts are per client (any acknowledgement clears it for the whole organisation).
38. **Unread notices** = `countUnackedNotices`: visible notices (status exactly `PUBLISHED`, targeting OR-filter, plus FUND notices restricted to `fundScope` when set -) minus those for which ANY receipt of the client has `acknowledgedAt`.

**C.4 Notifications (bell dropdown)**


39. `GET /notifications?limit=` (perm `lp.portal.view_notifications`; `limit` default 5, clamp 1..50) returns `{items:[...]}` merged from three sources then sorted by `createdAt` string desc and cut to `limit` :
 - `NOTICE`: latest 20 PUBLISHED/DELIVERED notices, skipping fund-disallowed ones and ones with a different `clientId`, and skipping notices the client has acknowledged; item `{id:"notif_notice_{id}", type:"NOTICE", title, fundName, href:"/lp-portal/notices?id={id}", createdAt:publishedAt}`. It does NOT evaluate `userId` targeting (a USER-targeted notice for a colleague appears) and does not apply `noticeVisible`.
 - `REQUEST`: up to 10 requests of the client with status in `OPEN, SUBMITTED, AWAITING_INVESTOR` ordered `updatedAt desc`; item `{id:"notif_req_{id}", type:"REQUEST", title:subject, fundName, href:"/lp-portal/requests?ref={reference}", createdAt:updatedAt}` (not fund-scope filtered).
 - `CAPITAL_CALL`: first 10 capital calls (`listCapitalCalls` page 1 size 10) with status in `ISSUED, OVERDUE, ACKNOWLEDGED`; item `{id:"notif_cc_{id}", type:"CAPITAL_CALL", title:"Capital Call #{callNo} due {dueDate|soon}", fundName, href:"/lp-portal/capital-activity?tab=calls", createdAt:"{dueDate}:00.000Z"|null}`.
 No `read` flag exists; there is no mark-as-read or dismissal; messages/threads are NOT in the feed (no `MESSAGE` item in the REST feed), although `lp_notification` socket pushes can carry `MESSAGE`/`REQUEST`/`NOTICE` types (rule 66). The feed is computed live, not stored (no notification table - not found in code).

**C.5 Service requests**


40. **Entity** `LpServiceRequest` : `reference unique VarChar(32), clientId, fundId?, requestType VarChar(64), status VarChar(32) default "OPEN", priority VarChar(16) default "NORMAL", subject VarChar(512), body Text, createdById?, assignedToId? (plain string, indexed, no FK), createdAt, updatedAt`. Messages `LpServiceRequestMessage` (5172-5183): `requestId, authorType VarChar(16) INVESTOR|OPS, authorId?, body, createdAt`. Attachments reference `requestId`/`messageId` in `LpPortalAttachment` (no relation declared).
41. **Reference format**: `SR-` + last 6 chars of upper-cased base-36 `Date.now` + 4 random upper-case base-36 chars, i.e. `SR-XXXXXXXXXX` (13 chars). No collision retry (unique constraint would 500).
42. **Create** `POST /requests` (SIGNATORY/MANAGER, perm `lp.requests.create`, Idempotency-Key required). Body `{type, fundId?, subject, description?, priority?, attachmentIds?}`. Rules: `fundId` -> `assertFundAccess`; `subject` required after trim else 422 `LP_VALIDATION` "subject is required" `fieldErrors:{subject:"Required"}`; `attachmentIds` must all exist for the client else 422 `LP_VALIDATION` "Invalid attachmentIds" `fieldErrors:{attachmentIds:"One or more attachments not found"}`; `requestType = upper(type || "PROFILE_ACCESS")`; `priority = upper(priority || "NORMAL")`; **no enum validation of type or priority**; `status = "SUBMITTED"`; `body = description || ""`; `createdById = user`. Then attachments are linked to the request (`requestId`), and, if `description` is non-empty, a first `INVESTOR` message with the same text is created (so detail `messages[0]` duplicates `description`). Response 201, message "Service request created", data = mapped request with `attachments`. Emits `lp_request_created` (rule 65). No subject/description max length check (database limit 512 for subject -> 500).
43. **Type vocabulary.** Code default `PROFILE_ACCESS` only; SRD lists `ACCOUNT_STATEMENT, CAPITAL_ACTIVITY, OPEN_ENDED_ACTIVITY, PROFILE_ACCESS`; the seed uses `PROFILE_ACCESS`. Others not enforced in code. **Priority** default `NORMAL`; the SRD example uses `HIGH`; the full set is not defined in code (not found in code).
44. **Status vocabulary.** Staff-settable list `REQUEST_STATUSES = SUBMITTED, OPEN, ASSIGNED, UNDER_REVIEW, AWAITING_INVESTOR, AWAITING_INTERNAL, RESOLVED, CLOSED`. Column default is `OPEN` but investor creation writes `SUBMITTED`. The SRD omits `OPEN` and `AWAITING_INTERNAL`.
45. **LP list** `GET /requests?status&type&fundId&page&pageSize` (perm `lp.requests.view`): where `clientId`, `fundId`, `status` (raw, exact), `requestType = type`; order `createdAt desc`; DB-level skip/take THEN in-memory fund-scope filter (so a page can be short and `total` over-counts when `fundScope` is set). Item = `mapRequest` + `attachments`. `mapRequest` : `{id, reference, type, fundId, fundName, status, priority (||"NORMAL"), subject, description (=body), submittedBy:{id,email,name}|null, createdBy (same object), createdAt, updatedAt}`; submitter name resolved from `User` (`firstName lastName` trimmed).
46. **Detail** `GET /requests/:reference` (perm `lp.requests.view`): 404 `LP_NOT_FOUND` "Service request not found" if `clientId` differs or fund not allowed; returns `mapRequest` + request-level `attachments` + `messages[]` ordered `createdAt asc`: `{id, authorType, authorId, body, attachments, createdAt}`. Message `authorId` is a user id; no author display name is returned for request messages (the thread detail has `participants`, request detail does not).
47. **Investor reply** `POST /requests/:reference/messages` (SIGNATORY/MANAGER, perm `lp.messages.reply`; NO Idempotency-Key): `body` required after trim (422 "body is required", `fieldErrors:{body:"Required"}`); request must belong to the client (404 "Service request not found") - fund scope NOT checked; attachments validated/linked to the message; message `authorType "INVESTOR"`; **if request status is `RESOLVED` or `CLOSED` it is set to `AWAITING_INVESTOR`** and `lp_request_updated {status}` is emitted - this is a questionable transition (the ball is with staff after an investor reply, not the investor) and is the ONLY automatic status change an investor action causes; replies on any other status leave status unchanged (so a request in `AWAITING_INVESTOR` stays there after the investor answers). Response 201 data `{id, authorType, body, attachments, createdAt}`.
48. **Staff service desk** (all `requireGpAdmin`): `GET /admin/requests?status&clientId&fundId&assignedToId&page&pageSize` (status upper-cased; default size 50, max 200; `createdAt desc`) -> items `{id, reference, clientId, clientName, fundId, fundName, requestType, status, priority, subject, assignedToId, messageCount, awaitingInternal, createdAt, updatedAt}` where `awaitingInternal = last message authorType==="INVESTOR" || no messages`. `GET /admin/requests/:reference` -> includes `clientEmail`, `body`, all messages (no attachments). `PATCH /admin/requests/:reference` body `{status?, assignedToId?, priority?}`: status must be one of the 8 values (else 400 "status must be one of:..."), priority upper-cased (no validation), `assignedToId` string or null; **assigning with no explicit status sets `ASSIGNED`** (even when the request was RESOLVED/CLOSED); empty patch -> 400 "Nothing to update"; any status can move to any status (no transition graph); no history/audit row. `POST /admin/requests/:reference/messages` body `{body}` creates an `OPS` message (authorId = staff user) and sets status to `AWAITING_INVESTOR` unless currently RESOLVED/CLOSED. **Staff replies emit no realtime event, no `lp_notification`, no email** (not found in code), so the investor only sees them on refetch.
49. **Attachments** (`LpPortalAttachment`, : `id att_<12 hex>, clientId, fileName, mimeType, storagePath, fileSizeBytes, sha256, requestId?, messageId?, uploadedById?`). Upload `POST /requests/attachments` multipart field `file` (SIGNATORY/MANAGER, perm `lp.requests.create`, no Idempotency-Key): no file -> 400 `LP_VALIDATION` "file is required"; empty buffer -> 422 "file is required"; **size limit 25 MB** (multer; overflow surfaces as 500 not 413); **no MIME whitelist, no per-request count limit, no virus scan** (not found in code). Stored on local disk `<cwd>/uploads/lp-portal-attachments/<clientId>/<id>_<sanitised name (max 200)>` with sha256; `mimeType` default `application/octet-stream`. Response 201 `{id, name, size, mimeType, downloadUrl:"/api/lp-portal/attachments/{id}/download", createdAt}`.
50. **Upload-then-attach protocol:** client uploads each file first (gets `id`), then sends `attachmentIds` on `POST /requests`, `POST /requests/:reference/messages` or `POST /messages/:id/replies`. `validateAttachmentIds` requires every id to belong to the client. Linking uses `updateMany... where requestId/messageId is null` so an already-linked attachment is silently not re-linked; unlinked uploads are never garbage-collected (not found in code). Download `GET /attachments/:id/download` (perm `lp.requests.view`, any role of the same client): 404 "Attachment not found" / "Attachment file missing"; `Content-Disposition: attachment` with the original filename. No audit on attachment download. Staff routes cannot list or download attachments (only via `?clientId=` impersonation on the LP route).

**C.6 Message threads**


51. **Entities** `LpMessageThread` (: `clientId, fundId?, subject VarChar(512), relatedType? VarChar(32), relatedId?, status default "OPEN" VarChar(16), lastMessageAt?`) and `LpMessage` (5204-5216: `threadId, authorType, authorId?, body, readAt?, createdAt`). **There is no participants table**: `participants` in the detail response are derived from message `authorId`s plus the caller, resolved against `User` -> `{id, email, name ("First Last"), initials}`. No role field is returned (the Nexus type has an optional `role`).
52. **Threads cannot be created through any API** - no investor or staff route creates an `LpMessageThread` and no staff route posts an `OPS` thread message; the only creators are the demo seed script (`relatedType:"SERVICE_REQUEST"`, `relatedId` = request id, `authorType:"OPS"`) (grep of `src`: only DESK/SESS reference the models). So the Messages tab can only show seeded/externally inserted threads (not found in code for staff compose/reply).
53. **`relatedType` / `relatedId`**: free strings (VarChar(32) / id); SRD says a thread links to a fund plus an optional call, distribution, dealing request, statement, request or document but code enforces none; the only observed value is `SERVICE_REQUEST`.
54. **List** `GET /messages` (perm `lp.messages.view`): where `clientId`, `fundId`, `status`; order `lastMessageAt desc, createdAt desc`; DB skip/take then in-memory fund-scope filter; per thread `unreadCount` = count of messages with `readAt null` AND `authorType "OPS"` (N+1 queries); `lastMessagePreview` = latest message body `slice(0,160)`; item `{id, subject, fundId, fundName, relatedType, relatedId, status, lastMessageAt, lastMessagePreview, unreadCount}`.
55. **Detail** `GET /messages/:id`: client-scoped 404 "Thread not found"; fund-scope enforced; returns `{id, subject, fundId, fundName, relatedType, relatedId, status, participants, messages[{id, authorType, authorId, body, attachments, readAt, createdAt}]}` ordered `createdAt asc`. Opening a thread does NOT mark it read (separate call).
56. **Reply** `POST /messages/:id/replies` (SIGNATORY/MANAGER, perm `lp.messages.reply`; no Idempotency-Key): `body` required (422 "body is required"); thread must belong to the client (fund scope NOT checked); attachments validated/linked; creates `INVESTOR` message; sets `lastMessageAt = now` and `status = "OPEN"` (reopens any status); emits `lp_thread_message` + `lp_thread_updated` + `lp_notification`. Response 201 `{id, authorType, body, attachments, createdAt}`.
57. **Mark read** `POST /messages/:id/read` (perm `lp.messages.view`, any role): sets `readAt = now` on all `OPS` messages of the thread with `readAt null`; returns `{threadId, markedRead:<count>}`; emits `lp_thread_read`. Read state is per MESSAGE, not per user: when one colleague reads, the whole organisation's unread count drops. Investor-authored messages are never counted unread.
58. **Unread (session badge)** = count of `LpMessage` where `readAt null`, `authorType "OPS"`, `thread.clientId = mine`, not fund-scope filtered.

**C.7 Organisation, colleagues, invitations, bank instructions**


59. **Organisation** `GET /organisation` (perm `lp.organisation.view`, any role): `{id, legalName, investorId, email, country, phone, address, status, lpRole (ctx.lpRole, null for staff), colleagues}`; `colleagues` only filled when `lpRole === "MANAGER"` or staff, errors swallowed to `[]`. `Client` also holds `type` and `taxId` which are not returned. `phone`/`address` nullable.
60. **Colleague entity** = `LpUserRelation` : `userId, clientId, lpRole VarChar(16) default VIEWER, isActive default true, fundIds Json?, invitedById?, revokedAt?, createdAt, updatedAt`, unique(userId, clientId). Roles: `VIEWER, SIGNATORY, MANAGER`.
61. **List** `GET /colleagues` (MANAGER or staff, perm `lp.organisation.manage_colleagues`; data = bare array): all memberships of the client including revoked, `createdAt desc`: `{membershipId, userId, email, name ("First Last", may have trailing space), lpRole, fundIds (array|null), isActive, status, revokedAt, mfaEnabled (UserMfaTotp.enabledAt present), lastActiveAt (User.lastSeen ISO|null)}`. `status = "SUSPENDED"` if `!isActive` or `revokedAt` else `"ACTIVE"`. The SRD status `INVITED` is NEVER produced: a pending invitee (never signed in) shows `ACTIVE`.
62. **Who may invite / update / revoke:** all three require `ctx.lpRole === "MANAGER"` or staff (route middleware and service guard). A MANAGER cannot grant role MANAGER (403 "Cannot invite another MANAGER via portal"; "Cannot promote to MANAGER via portal"); staff can. A MANAGER cannot revoke a MANAGER membership (403 "Cannot revoke manager via colleague API"); the staff-only `PATCH /admin/memberships/:id/revoke` has no such guard.
63. **Invite** `POST /colleagues` body `{email, role?, fundIds?}` (Idempotency-Key required): email trimmed + lower-cased (a missing email throws a TypeError -> 500, no validation); `role` default `VIEWER`; then `LpPortalInviteService.onboard`: find user by email else create (see rule 64); `fundIds` intersected with the inviter's `fundScope` when both are non-empty; existing membership: active -> 409 `LP_VERSION_CONFLICT` "User already has active access"; inactive/revoked -> reactivated (`isActive true, lpRole, fundIds, revokedAt null, invitedById`); none -> created. Response 201, message "Colleague invited", data = raw `LpUserRelation` row (no `invite` info: whether the email was sent is only `console.warn`ed). The staff variant `POST /admin/memberships` (`requireGpAdmin`) accepts `userId` OR `email` (+`firstName,lastName,lpRole,fundIds,clientId`), validates the client (404 "Client not found"), returns `{...membership, invite:{created, activationEmailSent}}` and for a NEW membership also overwrites `Client.userId` with the invitee (**DEF-457** the unique legacy link is rewritten on every new membership).
64. **Account creation + token + email** (invite service): email regex `^[^@\s]+@[^@\s]+\.[^@\s]+$` else 400 "A valid email address is required"; existing user -> linked, NO email sent; new user -> role must exist (`Role.name = "Limited Partner"` or contains it) else 500 "No 'Limited Partner' role exists - seed roles before inviting LPs"; created with `firstName = local part of email`, `lastName ""`, `roleCode "LIMITED_PARTNER"`, `mustChangePassword true`, bcrypt(10) hash of a generated 14-char temporary password (charset excludes 0/O/1/l/I; one upper, lower, digit, symbol `!@#$%*?`). Activation token: 32 random bytes hex, only its SHA-256 stored in `PasswordResetToken`, **TTL 7 days** (`INVITE_TTL_MS`), earlier unused tokens are burned. Email (nodemailer, from `getFromAddress("it")`, subject "{inviter} invited you to the {shortName} Investor Portal" or "You have been invited..."; `invitedByName` is not passed by the colleague route) contains the portal sign-in URL, the user's email, **the plaintext temporary password**, and an alternative link `{LP_PORTAL_URL || NEXT_PUBLIC_LP_PORTAL_URL || http://}/reset-password?token={raw}`. Send failure is logged and swallowed. A `resendInvite` method exists but no route calls it (not found in code).
65. **Acceptance** = the invitee signs in with the temporary password (then `mustChangePassword` forces a change) or opens `/reset-password?token=` which calls `POST /api/auth/reset-password {token,newPassword>=6 chars}`: marks the token used, sets the new password, `mustChangePassword false`, increments `tokenVersion`. Note: that endpoint also accepts the stored token HASH as the token, so a DB reader can reset passwords - contradicting the comment. There is no explicit "accepted" timestamp on the membership (not found in code).
66. **Patch colleague** `PATCH /colleagues/:membershipId` body `{role?, fundIds?}` : 404 "Membership not found" if other client; role MANAGER blocked for non-staff; `fundIds` intersected with the actor's scope; returns the updated row. NO last-manager guard (a manager can demote any manager including themselves; not found in code); no check that the target is active; no audit.
67. **Revoke** `PATCH /colleagues/:membershipId/revoke` (message "Colleague revoked"): sets `isActive false, revokedAt now` and increments `User.tokenVersion` in one transaction, which invalidates ALL the user's JWTs, including for other organisations. Revocation of a user who is also the legacy `Client.userId` leaves them with VIEWER access through the legacy fallback (DEFECT).
68. **Fund-scope privilege widening (DEFECT).** When an invite/patch supplies `fundIds` and the actor has a `fundScope`, ids outside the scope are dropped. If the result is empty (or `fundIds` omitted) the membership is stored with an empty/null `fundIds`, and `resolveAccess` treats empty as "all funds". A scoped manager can therefore create an unscoped colleague.
69. **Bank instruction changes** (`LpBankInstructionChange`, : `clientId, fundId?, status default "SUBMITTED", requestedById?, payloadJson Json, createdAt, updatedAt`). `POST /bank-instructions/changes` (SIGNATORY/MANAGER; perm `lp.organisation.view`; Idempotency-Key; 201): `fundId` -> `assertFundAccess`; if `policy.requireMfaForLp && !user.mfaEnabled` -> 403 `LP_MFA_REQUIRED` "MFA must be enabled to submit bank instruction changes"; row stored with `status "SUBMITTED"` and the ENTIRE request body as `payloadJson` (no field schema, no validation, no masking). `GET /bank-instructions/changes` (any role with `lp.organisation.view`) returns `{items:[{id, fundId, status, payload (raw JSON incl. whatever account numbers were posted), createdAt, updatedAt}]}` for the client. Only status `SUBMITTED` exists; maker/checker, verification, callback verification, approval, rejection, effective date and any staff route are **not found in code**. No notification/audit/realtime. The Nexus UI type expects `accountNumberMasked, bankName, requestedBy, submittedAt, fundName` which the API does not return.

**C.8 Settings, MFA, display**


70. **Notification prefs** `LpNotificationPrefs` unique(clientId, userId) : booleans `emailCapitalCalls, emailDistributions, emailDocuments, emailMessages, emailNotices, inAppCapitalCalls, inAppDistributions, inAppDocuments, inAppMessages, inAppNotices` (all default true); `emailDigest VarChar(16)` default `"WEEKLY"`; `presentationCurrency VarChar(8)` default `"USD"`; `defaultAsOfPreference VarChar(16)` default `"LATEST"`. **Nothing consumes these**: no email/in-app dispatcher, no digest job, no suppression logic reads them (grep of `src`: only the service-desk service). They are preferences storage only.
71. **GET /settings** (perm `lp.settings.view`, any role): `{notifications:{...10 booleans, emailDigest}, mfa:{requireMfaForLp, issuerName, enabled, enabledAt, manageUrls:{enroll:"/api/auth/mfa/enroll", confirmEnrollment:"/api/auth/mfa/confirm-enrollment", changePassword:"/api/auth/change-password"}}, presentationCurrency, defaultAsOfPreference}`; defaults applied when no row. The field is `emailDigest` (string); the Nexus UI type calls it `digest: "daily"|"weekly"|"off"` and `mfa.manageUrl/sessionsUrl/passwordUrl` (:644-646) - both differ from the API. Allowed `emailDigest` values are not validated (default `WEEKLY`; `DAILY`/`OFF` assumed by UI - not found in code).
72. **PATCH /settings/notifications** and **PATCH /settings/display** (both perm `lp.settings.view`; any role may edit own prefs; the second delegates to the first): accepts only the 10 booleans when `typeof === boolean`, plus `emailDigest`, `presentationCurrency`, `defaultAsOfPreference` when strings; unknown or wrongly typed fields are silently dropped; `upsert` on `(clientId, userId)`; user required (401 `LP_UNAUTHORIZED` "User required for notification prefs"); response is the flat 13-field object (not nested under `notifications`). `presentationCurrency` is not validated against a currency list (the Nexus legacy type allows `USD|ZIG`).
73. **Display prefs.** `presentationCurrency` (default USD) and `defaultAsOfPreference` (default `LATEST`) are stored per user but are NOT applied by the session payload: `session.presentationCurrency` is hard-coded `"USD"` and `defaultAsOfPreference` is read nowhere else (not found in code). Presentation currency is passed as a query param (`presentationCurrency`, upper-cased) to dashboard calls.
74. **MFA policy** = singleton `LpPortalMfaPolicy` id `"default"`: `requireMfaForLp Boolean default false`, `issuerName default "Arcus LP Portal"`. Staff (sysadmin only) `GET/PUT /admin/mfa-policy` body `{requireMfaForLp?, issuerName?}`. Effects of the policy: (a) login challenge only if policy ON **and** the user already has TOTP enabled - a user who never enrolled is NOT forced to enrol and logs in without MFA; (b) when the policy is ON, bank-instruction submission requires an enrolled TOTP (rule 69). If the policy is OFF, enrolled LP users are not challenged at login although the staff path challenges any enrolled user.
75. **MFA mechanics** (MFA service and auth controller): enrol `POST /api/auth/mfa/enroll` (authenticated) -> speakeasy secret (20 bytes), issuer = policy `issuerName`, label = email; secret stored AES-256-CBC with key = sha256(`MFA_ENCRYPTION_KEY` || `JWT_SECRET` || literal dev fallback "mfa-dev-key-change-me"); response `{qrDataUrl, manualEntryKey}`; re-enrolling resets `enabledAt` to null and clears backup codes. Confirm `POST /api/auth/mfa/confirm-enrollment {token}`: TOTP verify window +/-1 step; on success sets `enabledAt` and returns 8 backup codes (4 random bytes -> 8 uppercase hex chars each, stored as unsalted sha256 with `used` flags). Login: when MFA required the response is `{mfaRequired:true, mfaPendingToken}` (pending token = 32 random bytes hex, SHA-256 stored in `AuthMfaPending`, **TTL 5 minutes**, single user-slot, consumed (deleted) BEFORE the code is checked, so a wrong code needs a new password login); `POST /api/auth/mfa/verify {mfaPendingToken, token}` accepts a TOTP or an unused backup code, then issues a 7-day JWT with `aud:"lp"`. No disable/reset-MFA endpoint exists (not found in code). No TOTP attempt rate-limit is found in code.
76. **Colleague MFA/last-active:** `mfaEnabled` from `UserMfaTotp.enabledAt`; `lastActiveAt` = `User.lastSeen`, which login updates.

**C.9 Session payload**


77. `GET /session` (perm `lp.portal.access`) builds: **funds** = the client's `InvestmentCommitment` rows with `status IN (ACTIVE, PENDING)` ordered `createdAt asc`, filtered by `fundAllowed`, de-duplicated by `fundId`; per fund: `{fundId, publicReference (LpFundPortalContext.publicReference|null), fundName, shortName (ctx.shortName ?? fund name), operatingModel, currencyCode, shareClass, asOfDate, valuationStatus, investorAccountReference (LpHoldingPosition.accountRef|null), commitmentAmount (moneyStr 2dp)}`. Resolution rules: `operatingModel` = `LpFundPortalContext.operatingModel` if `OPEN_ENDED|PRIVATE_CAPITAL`, else `OPEN_ENDED` when `fund.fundPurpose === "LISTED_EQUITY"`, else `PRIVATE_CAPITAL`; `currencyCode` = ctx.currencyCode || commitment.currency || "USD"; `shareClass` = ctx.defaultShareClass ?? holding.shareClass ?? null; `asOfDate` = ctx.asOfDate || holding.asOfDate || today (UTC date); `valuationStatus` = ctx.valuationStatus || holding.valuationStatus || `"FINAL"`. Allowed `valuationStatus` values per SRD: `ESTIMATED | PROVISIONAL | FINAL | RESTATED` - the column is a free VarChar(16).
78. **Top-level**: `client:{id, legalName, email, investorId, displayName}` (displayName = ctx.displayName || "First Last" || email || legalName), `lpRole` (`ctx.lpRole || "VIEWER"` - staff impersonation shows VIEWER), `presentationCurrency` (**constant "USD"**), `defaultAsOfDate` = the maximum fund `asOfDate` (string sort) or today, `defaultValuationStatus` = the common status if all funds equal else `"FINAL"` (a mix of ESTIMATED and FINAL reports FINAL - DEFECT/choice), `funds`, `unreadCounts`.
79. **unreadCounts**: `requests` = count of the client's requests with status in `OPEN, SUBMITTED, UNDER_REVIEW, AWAITING_INVESTOR, ASSIGNED` (note `AWAITING_INTERNAL` excluded; this is "open requests", not "needing my attention"; not fund-filtered); `messages` = unread OPS messages (rule 58); `notices` = unacked notices (rule 38); `notifications = notices + requests + messages`. The bell feed (rule 39) uses a different status set and different sources, so the badge number and the dropdown length can disagree.
80. **LpFundPortalContext / LpHoldingPosition / LpComplianceStatus have no staff write path** in `src` (only the seed script and read services) - staff cannot configure operating model, valuation status, as-of date or holdings through any route (not found in code).

**C.10 Realtime**


81. **Transport:** Socket.IO v4 on the API HTTP server, path `/socket.io`, CORS `origin:true, credentials:true`. Discovery endpoint `GET /api/lp-portal/realtime` (perm `lp.portal.access`) returns `{transport:"socket.io", url (API_PUBLIC_URL or http://127.0.0.1:{PORT||3009} minus trailing /api), path:"/socket.io", auth:{token:"Bearer <jwt> via handshake.auth.token"}, autoRooms:["user:{userId}","lp_portal:{clientId}"], subscribe:{...}, events:{...}}`. Nexus type `LpRealtimeInfo {enabled, wsUrl, namespace, events[], pollingIntervalMs}` does not match this shape.
82. **Handshake auth:** token from `handshake.auth.token`, `Authorization` header or `query.token`, "Bearer " stripped, `jwt.verify` with `JWT_SECRET` (default literal fallback in code); on missing/invalid token the connection is STILL accepted unauthenticated (`next`), without `userId`. Authenticated sockets auto-join `user:{userId}` and, if an ACTIVE `LpUserRelation` exists, `lp_portal:{clientId}` (first relation only). `join_lp_portal` re-joins the org room (authenticated only).
83. **Detail rooms** `join_lp_thread {threadId}` -> `lp_thread:{id}`, `leave_lp_thread`, `join_lp_request {reference}` -> `lp_request:{ref}`, `leave_lp_request`. **No authorisation check on these joins** - any socket (even unauthenticated) that knows a thread id or request reference can subscribe and receive message payloads (security DEFECT).
84. **Events (server -> client) and emitters** (realtime service):
 - `lp_notice_updated` -> room `lp_portal:{clientId}`; payload `{type:"NOTICE", noticeId, title, status (OPENED|ACKNOWLEDGED|PUBLISHED), fundId, fundName, href:"/lp-portal/notices?id={id}", at}`. Fired on first open and on acknowledge. `PUBLISHED` is never emitted (rule 33). Also pushes `lp_notification` with the same payload to ALL active org users **including the actor** (no exclusion).
 - `lp_request_created` -> org room + `lp_request:{ref}`; payload `{request, type:"REQUEST", requestId, reference, subject, status, priority, fundId, fundName, href:"/lp-portal/requests?ref={ref}", at}` + `lp_notification` to org users except the actor.
 - `lp_request_message` -> `lp_request:{ref}`; payload `{type:"REQUEST_MESSAGE", reference, message, href, at}`; additionally `lp_request_updated` (same payload) -> org room; `lp_notification {type:"REQUEST", title:"New message on request {ref}", href, reference, at}` to others.
 - `lp_request_updated` -> `lp_request:{ref}` + org room; payload `{reference,...patch, at}`; emitted ONLY when an investor reply reopens a RESOLVED/CLOSED request. Staff status changes emit nothing.
 - `lp_thread_message` -> `lp_thread:{id}`; payload `{type:"THREAD_MESSAGE", threadId, subject, fundName (always null here), message, href:"/lp-portal/requests-messages?thread={id}", at}`; `lp_thread_updated` -> org room (same payload); `lp_notification {type:"MESSAGE", title:"New message: {subject}"|"New portal message", href, threadId, at}` to others.
 - `lp_thread_read` -> thread room + org room; payload `{threadId, markedRead, at}`.
 - `lp_notification` -> `user:{userId}` for each ACTIVE org user (excluding the actor where passed). Types seen: `NOTICE, REQUEST, REQUEST_MESSAGE?, MESSAGE`; the doc also lists `THREAD_MESSAGE` (payload type of the thread event) - the `lp_notification` item itself is typed `MESSAGE`.
 - The thread href uses `/lp-portal/requests-messages?thread=` while notification hrefs for requests use `/lp-portal/requests?ref=`; the Nexus route set must resolve both (cross-check with UI routes).
85. **Events NOT emitted** (not found in code): document published, capital call issued, distribution, colleague invited/revoked, staff reply to request, staff status change, notice created, settings change.
