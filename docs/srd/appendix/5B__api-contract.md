# API CONTRACT (from the 5B draft)

This block specifies the 70 methods of `lpPortalApi` (`lib/api/lp-portal-api.ts`) as the contract Nexus implements. The "Real mounted path" and "Service" columns describe the reference implementation (NVCCZ); the Nexus mount point is proposed as `/api/v1/lp-portal/*` (the UI base path is `/lp-portal`, Q-153: keep `/api/v1/investor/*` as an alias for the four legacy routes — default: no alias). The reference router has 83 routes: the 70 below, 13 not called by the UI (listed in the second table) and one cron route; a `lp-portal-swagger-paths` file documents only 22 of them and is not a source of truth. Every number inside `data` is serialised as a string in the reference backend; the UI coerces a fixed list of count keys back to numbers.

Conventions used in the tables (reference backend):

- Real mounted path = `/api/lp-portal` + "Path" (router mounted at `/api/lp-portal`; cron router at `/api/cron/lp-portal`). The UI `BASE` is `/lp-portal`, so the only difference between UI path and real path is the `/api` prefix; relative paths are identical for all 70 methods (no renamed route). Express route order is correct for the literal-vs-param pairs (`/capital-calls/summary` before `/:id`, `/distributions/statement/download` before `/:id`, `/documents/summary` before `/:id`, `/dealing/requests/export` before `/dealing/requests`).
- **Gate R** = `authenticate` (Bearer JWT) then `lpPortalContract` then `requireLpPortalAccess` then `requireLpPermission(code)`. **Gate S** = Gate R + `requireLpSignatory` (SIGNATORY or MANAGER or staff). **Gate M** = Gate R + `requireLpManager` (MANAGER or staff). The permission code in the cell is the one passed to `requireLpPermission`.
- `C` = `src/controllers/LpPortalController.ts`; services are in `src/services/lpPortal/`. `Idem(x)` = `requireLpIdempotencyKey("x")`.
- "any number in `data` is serialised as a string" is a global behaviour (see NOTES); fields shown as number below are strings on the wire.

**C. Envelope, errors, pagination, headers, idempotency, rate limits**

Success envelope (`successBody`): `{success:true, message?, data, timestamp (ISO), meta:{requestId}}`.
- List envelope (`listBody`): `data = {items, page, pageSize, total, totalPages}` (`totalPages = ceil(total/pageSize)`).
- **Every number inside `data` becomes a string** (`decimalSafe` converts numbers, bigint and Decimal to strings, Dates to ISO). This includes `page`, `pageSize`, `total`, `totalPages`, `callNo`, `unreadCounts.*`, `noticeDays`, `openCount`, `investmentCount`, sizes. Booleans stay booleans. The UI coerces a fixed key list (`page, pageSize, total, totalPages, count, unreadCount, investmentCount, portfolioCompanyCount, newThisWeek, requiresSignature, secureDownloadsYtd, openCount, paidCallCount, dueSoonCount`) back to numbers (`coerceLpCounts`); other numeric-string fields (`callNo`, `noticeDays`, `size`, `fileSizeBytes`, `pageCount`, `settlementLagDays`, `maxFileMb`) stay strings. Money, units, rates and multiples are decimal strings by design (money 2dp, units up to 6dp trimmed, NAV and rates up to 8dp trimmed, ratios 4dp).
- `meta.requestId` is a fresh random UUID per response (`successBody`/`errorBody` always set `meta`), so it does NOT equal the `X-Request-Id` response header; `lpPortalContract` only fills `meta` when absent. `X-Request-Id` request header is honoured when it matches `^[A-Za-z0-9][A-Za-z0-9._:-]{0,127}$`, otherwise a UUID is generated; it is echoed in the `X-Request-Id` response header.
- `GET /reports` (#69) returns `{success, data:[...], pagination, timestamp, meta}` (flat, not nested).
- Binary routes return no envelope: capital-call notice, distribution notice and statement are generated `text/plain` stubs; documents, vault and report downloads are file bytes; CSV exports are `text/csv`; the `xlsx/pdf` account-activity export and non-csv dealing export return JSON.

Error body (`errorBody`, used by `LpPortalError` and the LP error handler): HTTP status per error and
`{success:false, message, error:{code, message, fieldErrors?:{<field>:<message>}, details?:<object>, retryable:false}, timestamp, meta:{requestId}}`. The UI's `LpApiErrorBody` has `code/message/fieldErrors/details/retryable` at the top level, so the UI client must read `error.*` (or flatten). `retryable` is always false in the code read.

Errors that do NOT use the LP body (plain `{success:false,message}`, no `code`): `authenticate` 401 "Unauthorized" (missing/invalid/expired Bearer token, user not found, tokenVersion mismatch); user-availability 403 `{success:false, code, message}`; `requireLpPortalAccess` failures (401 "Unauthorized", 400 "GP staff must pass ?clientId= for LP portal impersonation", 401 "No active LP portal access", 404 "Client not found"); `requireGpAdmin` 403 "GP Ops access required"; `requireSysAdmin` 403 "SysAdmin access required"; the missing-file 400s of #12/#52 (`code` LP_VALIDATION inside `error`) and B11 (no `error`); cron 401/403/500.

Error handler mapping (`lpPortalErrorHandler`, mounted last on the router): `LpPortalError` as thrown; any error with `statusCode` or `status`: 401 `LP_UNAUTHORIZED`, 403 `LP_FORBIDDEN`, 404 `LP_NOT_FOUND`, any other status `LP_VALIDATION` (message passed through); anything else 500 `LP_EXPORT_FAILED` with the raw `err.message` (even for non-export routes; multer size errors land here).

Idempotency (`requireLpIdempotencyKey`, applied after the permission checks, so an unauthorised caller gets 403 before any key error):
- Routes (9): `POST /capital-calls/:id/acknowledge` (`capital-call-ack`), `POST /capital-calls/:id/payment-confirmations` (`capital-call-payment`), `POST /dealing/subscriptions` (`subscription`), `POST /dealing/redemptions` (`redemption`), `POST /jobs/performance-report` (`perf-report-job`), `POST /notices/:id/acknowledge` (`notice-ack`), `POST /requests` (`service-request`), `POST /bank-instructions/changes` (`bank-instruction-change`), `POST /colleagues` (`invite-colleague`). These 9 are the only routes that use it (attachments upload, replies, patches, read marks and settings do not).
- Header `Idempotency-Key`: required, must match `^[\x21-\x7e]{8,200}$` else 400 `LP_VALIDATION` "Idempotency-Key header required (8–200 printable ASCII)".
- Store: table `lp_portal_idempotency_keys` (`clientId, userId, scope, idempotencyKey, payloadHash (sha256 of JSON.stringify(req.body ?? {})), statusCode, responseJson LongText, createdAt`), unique on (`scope`, `idempotencyKey`), where `scope = "<clientId>:<action>:<METHOD>:<req.path>"` (path includes the record id). **TTL / purge: not found in code** (no expiry column, no cleanup job found).
- Replay: same scope+key and same payload hash: the stored status code and body are returned verbatim with header `Idempotent-Replay: true` (the handler is not run). Same key with a different payload hash: 409 `LP_IDEMPOTENCY_KEY_REUSED`. Only 2xx responses are stored; the insert is fire-and-forget and errors are swallowed; the check is not atomic (two concurrent first requests both execute). For multipart routes the hash is taken before multer parses the body, so it is the hash of an empty body (no payload-conflict detection).

Pagination: `parseListQuery`: `page` >= 1 (default 1); `pageSize` taken from `pageSize` else `limit` (default 50, min 1, max 200); also parsed but unused by the services: `sortBy`, `sortDirection`/`sortDir` (all lists use a fixed order, newest first), `search`. `fundId=all` is treated as no filter. Lists using `listBody`: capital calls, distributions, account activity (not really paginated), dealing requests, documents, notices, requests, message threads. Capital calls, distributions, documents, notices and account activity paginate in memory after loading everything; dealing requests, requests and threads use DB `skip/take`. `getDashboardRecentActivity` and `getNotifications` use `limit` clamped 1..50. `GET /reports` uses `limit` (default 20, no cap).

Rate limiting: no LP-specific or router-level rate limiter found in `lpPortalRoutes.ts` or `app.ts` for `/api/lp-portal` (the `express-rate-limit` usages in the repo are vendor-portal, homepage and newsletter routes). Body limits: JSON 100 kb globally; multipart files 25 MiB (multer memory storage) on payment confirmations, subscriptions, request attachments and `/admin/documents`.

Headers: request `Authorization: Bearer <JWT>` (7-day token; `authenticate` loads the user, checks status/validity window and `tokenVersion`; the JWT `aud` claim is not verified), `Idempotency-Key`, optional `X-Request-Id`; response `X-Request-Id`, `Idempotent-Replay: true` on replays, `Content-Type` and `Content-Disposition` on downloads. CORS is an allow-list in `app.ts` (includes `lp.nvccz.online` and `app.arcus.co.zw`; the Nexus investor host is not in the list read, so the Nexus host would have to be added; not verified beyond the list prefix read).

Cross-cutting behaviours worth carrying into the Nexus SRD:
- The call "id" in every capital-call URL is the investor allocation id, and the distribution "id" is the distribution allocation id; ledger entry ids can be call allocation, payment or distribution allocation ids; service requests are addressed by `reference` ("SR-" + 6 base36 time chars + 4 random chars, upper-case), threads by id.
- Visibility rules: capital calls appear only when issued (not DRAFT/CANCELLED and notices sent or a post-issue status); distributions only when not DRAFT/CANCELLED; the ledger and recent-activity feeds do not apply the call-visibility rule.
- Derived call status has a precedence quirk (ACKNOWLEDGED outranks OVERDUE).
- Document reads write audit rows (`lp_document_access_audit`: VIEW, DOWNLOAD, PREVIEW with user, IP, user agent); `secureDownloadsYtd` counts DOWNLOAD rows.
- Realtime events are pushed on notice open/acknowledge, request create/message/update, thread message/read, and a per-user `lp_notification` to the other users of the client; staff replies and staff notice creation do not push (not found in code).
- Unknowns / not found in code: idempotency TTL; any staff route to create threads, bank accounts, dealing rules, holdings, compliance status or fund portal context, or to review bank-instruction changes or dealing requests; payment-confirmation review; email on investor actions; rate limits; `LP_FILE_TOO_LARGE`; per-fund notice entitlement check; accreditation enforcement on dealing.
