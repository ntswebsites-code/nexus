### 1.2 How a bridge hooks the DOM and the API

1. `admin-99-boot.js` calls `mx.boot(...)`: `mx.loadMe()` (`GET /api/auth/me`, sets `mx.user` with `permissions[]`), then runs every loader registered with `mx.onLoad(perm, fn)` whose permission the user holds. Loaders write results to `mx.data.<key>`. Success sets `mx.live = true` and `<html data-mx-live="1">`. A 401 or network failure leaves `mx.live=false` and the prototype shows demo data.
2. The prototype scripts then evaluate; the data hooks make their globals start from `__mxData`.
3. Behaviour is changed without touching markup, in three ways:
   - `mx.intercept(selector, handler, {when, thenNative})`: capture-phase click on `document`, stops the prototype handler, runs the API call, optionally replays the native click so the prototype updates its own UI.
   - `mx.interceptSubmit(selector, handler)`: same for form submits.
   - `mx.wrapGlobal(name, wrapper)`: replaces a prototype global function (for example `hasPermission`, `navigate`, `renderRoleSwitcherV8`, `uploadDocument`, `togglePermissionV8`, `saveSettingsV8`) with a wrapper receiving `(original, args)`.
4. UI built by bridges reuses prototype widgets: `openDrawer`/`closeDrawer` (`#detailDrawer`), `mx.modal` (the V34 modal `#v34Modal`), `toast()` (`#toastStack`), detail-grid/detail-section classes. No new CSS.
5. API base: `window.__MATANHO_API__` (set by the runtime), paths are absolute (`/api/v1/...`, `/api/auth/...`). Cookie session with `credentials:'include'`. Step-up: a `401 step_up_required` triggers `window.prompt` then `POST /api/auth/mfa/step-up`, then one retry.
6. Existing live behaviour (what works today in `/classic`):
   - clients and cash accounts: list, create, profile edit, cash-account lifecycle (`/clients`, `/cash-accounts`).
   - investor services: work queue from service requests, capital notices, documents, secure messages (`/client-ops/services/*`, `/documents`).
   - onboarding and KYC: `/kyc/cases/legacy`, advance, evidence, messages, screening.
   - vault: list, upload, new version, export, submit/approve/publish (`/documents`).
   - private markets: only the company-reporting review card (`/private-markets/...` company staff routes).
   - RBAC, settings, audit: role context, matrix, users, policy, SoD, settings, hash-chained audit with filter and CSV (`/admin/*`).

### 1.3 Page switching, nav, role switcher, permissions in the prototype

- `navigate(page)` (01-inline.js:361): checks `permissionForPage(page)` against `hasPermission()`, then toggles `.page.active[data-page]` and `.nav-item.active`. No URL path; the hash is read by v-scripts for deep links. Denial toast: "Access restricted".
- `hasPermission(p)` = `rolePermissions[state.role].includes(p)`. `state.role` defaults to `__mxData.role` (hook), else `investment_director`.
- Sidebar items carry `data-page` and `data-permission` (`03-sidebar.html`). V16 `applyRoleNav()` (07-v16-focus-script.js:47) splits items into focused (`rolePrimary[role]`) and secondary; the "All workspaces" toggle flips `nav.dataset.expanded`. Permissions on `data-permission` are enforced by `applyRolePermissions`-style scripts that hide items the role lacks.
- Role switcher `#roleSwitcher` (`renderRoleSwitcherV8`, 02-v7): lists all 10 prototype roles from `roleLabels`.
- What the live session drives today (`admin-60-access.js`): `GET /api/v1/admin/access-context` returns `{roles, role, roleLabels, rolePermissions}`; `hasPermission` is wrapped so that when `state.role === mx.data.role` the answer is the UNION of all the user's real permissions (`mx.user.permissions`); the switcher is rewritten to the roles the user really holds, plus "Preview · <role>" entries. `/api/auth/me` is the identity and permission source; `GET/PUT /api/v1/shell/me/role-focus` stores a per-user "hat" (admin-60 does not use it yet; the native shell does).
- Page set: all 28 pages exist as fragments 06 to 33, the detail layer `34`, and the sidebar, topbar, drawer, modals, copilot FAB. The nav item count in `rolePrimary` is "28 available".

## 3. Wiring architecture

### 3.1 Principles
- Markup (`src/legacy/markup/*`) and CSS (`public/legacy/css/*`) stay byte-identical to the original. Only exception: sidebar restore (1.4).
- All behaviour lives in `src/legacy/bridge/*.js` and `DATA_HOOKS` text patches in `tools/legacy-bridge.mjs`. No new design: use `openDrawer`, `mx.modal`, `toast`, existing table/chip/detail classes.
- Live when signed in; signed out or API down means the prototype shows its own demo data (existing behaviour), but a NEW flag `mx.strict` (live and permitted) turns demo seeds and localStorage state off per page, so no demo rows appear next to real ones (as already done for KYC seed cases and RBAC).

### 3.2 Shared client (owned by package W0, extends `mx-core.js`)
Extend `window.mx` (do not create a second client):
1. Envelope: `mx.api(method, path, body, opts)` returns `data` for `{data}` envelopes, the bare payload otherwise (copy `unwrap` from `src/ops/api.ts`); `mx.list(path, params)` returns `{rows,total,page,pageSize}`; `mx.qs(obj)`.
2. `Idempotency-Key` header on every POST/PUT/PATCH by default (`mx.uuid()`), reused on step-up retry. Option `opts.idem=false` for safe GETs only.
3. `If-Match`: `opts.version` sets `If-Match`; helper `mx.versioned(row)` reads `row.version`. On `409 version_conflict` show the server message and re-fetch.
4. Step-up: replace `window.prompt` with a prototype-styled modal (`mx.modal`) asking the 6-digit code; keep one-shot retry with the same Idempotency-Key. Handle `step_up_cancelled` quietly.
5. Errors: `mx.fail(err)` maps `fieldErrors` into a message list and, when a form is passed, marks inputs with the prototype's invalid style (`aria-invalid` plus toast text). Special codes: `segregation_of_duties`, `forbidden`, `not_implemented` (501 shows "Not available yet"), `conflict`.
6. Toasts: always `window.toast(title, msg, 'error'|'success')` (prototype `#toastStack`); fall back to `mx.toast`.
7. `mx.upload(file, ...)`, `mx.download(path, name)` (already present), `mx.table(el, rows, cols)` helper that re-renders a `<tbody>` using the existing row classes, `mx.hydrate(page, fn)` that runs `fn` once when `navigate(page)` first activates the page and again on refresh (wraps `navigate`), `mx.refresh(page)` for after-write reloads.
8. `mx.strict(page)`: true when `mx.live && mx.can(<page permission>)`; page bridges use it to skip demo seeds and to guard localStorage.
9. Pagination and sorting: staff list endpoints page server side (`page`, `pageSize`, `sort`); the prototype's search/filter ids call the API with `q`/filter params (debounce 250 ms), rather than filtering client-side.

### 3.3 Hydrating each fragment
1. Declare the page loader with `mx.onLoad(perm, fn)` ONLY for light summary data (badge counts). Heavy page data loads lazily on first `navigate(page)` through `mx.hydrate`, keeping boot under the 15 s bridge timeout.
2. For arrays the prototype reads at start (`portfolios`, `orders`, `cashJournals`, `cashReservations`, `cashExpectations`, `statementImports`, `reports`, `research`, `institutionalPositions`) add DATA_HOOKS (`live('key')`), as the existing hooks do. Prefer re-rendering via the prototype's own render function after the first lazy load (call `window.renderOrders()`-style functions after replacing the array in place with `mx.replace(array, rows)`).
3. Row/field mapping lives in each bridge as `toProto(apiRow)`; the prototype shape is the contract, not the API shape.
4. Writes: `mx.intercept('[data-action="x"]', apiCall, {thenNative:true})` where the prototype's UI update is safe, otherwise `mx.hydrate` refresh after the call.
5. Localstorage keys that hold domain state (list in section 5) are ignored when `mx.strict`.

### 3.4 Permissions and role switching
- Source of truth: `/api/auth/me` (`permissions[]`) and `GET /admin/access-context` (roles). Keep `admin-60`'s `hasPermission` wrapper (union across held roles).
- Sidebar: after boot, for each `.nav-item[data-page][data-permission]` hide it when `!mx.can(perm)` (prototype `applyRolePermissions` still runs; this adds the real union). Pages the prototype gates with coarse view codes (`dashboard.view`, `portfolio.view`, `orders.view`, ...) must exist in the seeded permission catalogue (verify `tools/ws0-role-catalog.mjs` and `prisma/seed-admin-core.ts`; add missing codes to the catalogue in package W0, not in markup).
- Control-level checks: hide or disable a button when the backend permission it needs (for example `orders.create`, `orders.approve`) is missing: `mx.gate(el, perm)`.
- Role switcher: keep admin-60 behaviour (real roles plus "Preview" entries) and connect it to `PUT /shell/me/role-focus` so a "hat" narrows nav focus; API authorisation always stays the union.
- Badges (`<em>` counts) must be replaced by live counts or removed (`mx.badge(page, n)`), never left at the demo numbers.

### 3.5 Entry point and demotion of /ops
1. `next.config.ts`: `'/' -> '/classic'` (or serve the prototype at `/` and rename `/classic` to `/`; decide once, keep `/classic` as alias). Update `proxy.ts` matcher and login `next` default.
2. Move `app/(ops)/ops/**` and `src/ops/*` to `/ops-native` (route folder rename plus `basePath`-style link prefixes: grep `'/ops'` in `src/ops`), not linked from the prototype; add a tiny unlisted link in the profile drawer for staff with `admin.settings`.
3. Delete `admin-01-retired.js`, restore the 28-item sidebar, retarget the "Operations Console" link in `admin-99-boot.js`, remove the `Open the new workspace` link.
4. `/ops` and other native deep links (`LegacyHashRedirect.tsx`) are inverted: native hash redirect not needed; keep a redirect `/ops/* -> /ops-native/*` for bookmarks.
5. API and database are untouched by this demotion.

### 3.6 Testing

## 5. Risks and prototype assumptions the backend contradicts

R1. Sidebar was edited (20 nav items removed and a link to `/ops` added). Restore from `0adef6f` before anything; verify with `git diff 0adef6f -- src/legacy/markup`.
R2. Script load order. v33 to v56 patch earlier functions by re-declaring globals. `wrapGlobal` works on `window.<fn>` only for functions declared with `function name(){}` at top level of a classic script; `const`/`let` globals (for example `let orders`, `const portfolios`, `const clients`) are NOT window properties, so they can only be hooked by text patch (`DATA_HOOKS`) or replaced in place (`mx.replace`). Each package must test which mechanism applies per symbol.
R3. localStorage as the prototype's database (keys: `matanho-v37-orders`, `-v53-submitted-orders`, `-v56-submitted-orders`, `*-order-draft`, `matanho-recon-v12`, `matanho-v53-counterpart-imports`, `matanho-v52-financing`, `matanho-cash-accounts-v43`, `matanho-client-profiles-v10`, `matanho-onboarding-v10`, `matanho-scenarios-v8`, `matanho-portfolio-view-v8`, `matanho-v53-evidence-requests`, `matanho-v39-orders-metrics`). Live pages must neither read nor write these (guard by `mx.strict`); otherwise demo data reappears and different users share browser state.
R4. Hard-coded ids and demo references. Prototype rows use ids like `ORD-...`, `CL-...`, portfolio codes; the API uses its own refs (`lib/refs.ts`) and UUIDs. Mapping layer `toProto` must carry the real id in `data-id` attributes; text matching on demo names will break.
R5. Role model mismatch. Prototype: one active role at a time, 10 fixed roles, coarse permission codes (`orders.view`...). Real: multiple roles with permission UNION, fine-grained codes (`orders.create/approve`, ...), maker-checker and segregation of duties enforced server side. The prototype will show buttons the user cannot use unless `mx.gate` is applied; and an in-prototype "approve own order" flow will be rejected (`segregation_of_duties`). Preview roles must be read-only.
R6. Step-up and MFA. Approvals, releases and signatures can answer `401 step_up_required`. `window.prompt` is crude; replace in W0. Users without MFA enrolled hit a dead end: surface `mx.mfaSetup()`.
R7. Idempotency and concurrency. mx-core does not send `Idempotency-Key` or `If-Match` today; double-click and stale-edit protection is missing. Orders, journals and limits use `version` / `If-Match`.
R8. Static numbers in markup (sidebar badges, command-centre KPIs, "28 available", chart axes, sample dates in 2026-08). Must be replaced by computed values or hidden; a mixture of live and static numbers is the biggest credibility risk.
R9. Missing backend for some prototype controls: portfolio create (no `POST /portfolios` found), data "products" tab, report editor free-text bodies, command-centre aggregate AUM series, `performance-methodology`, `account-control-rules`. Each needs a decision: implement route, or render as informational with honest empty state (never fake success). Record in `docs/DECISIONS-NEEDED.md`.
R10. Integrations in sandbox mode (LLM for copilot, FIX/broker routing, market data, custodian feeds): buttons must show the integration banner state (`/admin-core/integrations/banner`) instead of implying live trading or data. `501 not_implemented` must be rendered as "Not available yet".
R11. Bridge boot budget. `LegacyScripts` waits at most 15 s and evaluates scripts after boot; loading 20 pages of data at boot would blow it. Load heavy data lazily (3.3 item 1).
R12. CSP and inline handlers. The proxy CSP allows `unsafe-inline`, but any bridge fetch to a different origin than `NEXT_PUBLIC_API_URL` is blocked; connect-src is `self` plus the API only.
R13. Pagination. Staff lists return pages (default 25?); prototype tables assume full arrays and client-side search/sort. Use server filters or fetch pages until `total` for small catalogues; never silently truncate (show "showing n of total").
R14. `extract-legacy.mjs` re-extraction overwrites fragments and removes hooks unless `applyBridge` runs after it; it reads git history by rev. Do not re-run it casually; W0 owns it.
R15. Files and evidence. Downloads use short-lived signed URLs (`/download-url`); the prototype's blob/base64 evidence paths (`getEvidenceBlob35`, IndexedDB) must not be used for live records.
R16. Concurrent work. Admin portal files are touched by other branches (`feat/investee-native` has modified `portals/company-web` and backend only; low conflict). The `app/(ops)` rename touches many imports; W0 should do it in one commit on its own branch.
